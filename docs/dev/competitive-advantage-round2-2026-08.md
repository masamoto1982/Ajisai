定義しない。正典は `spec/` 配下のソースと、そこから生成される `SPECIFICATION.html`

対象読者: 言語設計者本人、および次の改修指示書を書く担当。
前提: `docs/dev/competitive-advantage-work-order-2026-08.md`（Phase 1〜5、完了済み）

## 0. 要約

本書の主張は一つ。

> Ajisai の真の資産は「正確な数」でも「契約」でもない。それらは単体なら他言語も
> 追随できる。追随できないのは、**Ajisai の意味論が有限で、列挙可能で、厳密に
> 決定可能な一個のデータ構造である**という事実のほうだ。
> ならば言語は「読ませるもの」をやめ、**計算して出荷するもの**にすべきである。

65 語・平坦辞書・import なし・60 語が固定アリティ・6 値ドメイン・全域比較・
決定的・I/O なし・内容アドレス同一性・観測全体を畳む 32 バイトのダイジェスト。
この組み合わせを持つ言語は他にない。この組み合わせがあるとき初めて、
**言語仕様そのものを機械可読な生成制約として配れる**。

以下、層 0（土台の修理）から層 4（計算の証明書化）まで、12 の提案を挙げる。
層 0 は他のすべての前提なので、先に読むこと。

## 1. 層 0 — 土台の修理：アリティ推論は現在 **不健全**である（確認済みバグ）

### 1.1 何が起きているか

`check --contract` の看板は「保守的であり、**偽の error は決して出さない**」
（README「Safety model」、SPEC `LANG.CONTRACT.CHECK`）。この不変条件は
`word_space.rs` のモジュールコメントでも "never a false error" として明示されている。

**この不変条件は、アリティ軸において現在破れている。** しかも破れる条件は
「本体にベクタリテラル `[ ... ]` かコードブロック `{ ... }` を含む」——
すなわち現実の Ajisai コードのほとんどである。

### 1.2 再現（この repo の HEAD、`cargo build --bin ajisai` 済み）

```ajisai
#:contract DOUBLE-ALL ( 1 -- 1 )
{ { 2 MUL } MAP } 'DOUBLE-ALL' DEF
```

```console
$ ajisai check t.ajisai --contract --json
"`#:contract DOUBLE-ALL`: declared arity ( 1 -- 1 ) but inferred ( 2 -- 1 )."   severity: error
$ echo '{ { 2 MUL } MAP } '"'"'DOUBLE-ALL'"'"' DEF
[ 1 2 3 ] DOUBLE-ALL' > u.ajisai && ajisai run u.ajisai --json
status ok   stackDisplay ["[ 2/1 4/1 6/1 ]"]      # 実アリティは ( 1 -- 1 )
```

同じ壊れかたを、ベクタリテラルでも 2 通り確認した。

| 定義 | 真のアリティ | 推論結果 | 判定 |
| --- | --- | --- | --- |
| `{ [ 1 2 ] } 'PAIR' DEF` | `( 0 -- 1 )` | `( 0 -- 2 )` | 偽 error |
| `{ [ 10 20 ] ADD } 'ADD-PAIR' DEF` | `( 1 -- 1 )` | `( 0 -- 1 )` | 偽 error |
| `{ { 2 MUL } MAP } 'DOUBLE-ALL' DEF` | `( 1 -- 1 )` | `( 2 -- 1 )` | 偽 error |

いずれも `confidence: "complete"` で返る。つまり保守的 `note` に落ちる経路すら
通らず、**証明済みの違反として `error` を出し、exit 1 になる**。

### 1.3 原因

`rust/src/interpreter/word_contract.rs` の `infer_word_contract_inner` の走査で、
`Token::VectorStart` / `VectorEnd` / `BlockStart` / `BlockEnd` は
`sim.feed_structural` に渡るだけで **`FlowAccumulator` には何も伝えない**。
一方、区切りの内側にある `Token::Number` / `Token::String` は `flow.push_literal()`
を、`Token::Symbol` は `flow.apply(...)` を、外側と区別なく実行する。

結果、`[ 1 2 ]`（実行時はスタック高 +1）は高さ +2 と数えられ、
`{ 2 MUL }`（実行時は +1、中身は評価されない）は「2 を積んで MUL を適用」
として **インライン展開**されてしまう。区切りトークンは意味を持つのに、
アリティ計算だけがそれを見ていない。

### 1.4 なぜこれを最初に置くか

以下の提案はすべて「推論が健全である」ことを前提に価値を持つ。
土台が偽 error を出す限り、その上に何を積んでも信用の総量は増えない。
**層 1 以降に着手する前に、ここを閉じること。**

なお、これは `docs/dev/spec-impl-drift-tactic.md` の裁定対象（正典の記述と実装の
食い違い）に該当するので、修正方針は同文書の手順に載せるのが筋である。

## 2. 層 1 — 推論を「諦めない」ものにする

現状の推論は、少しでも難しい構造に当たると `Unbounded` / `Conservative` に落ちる。
実測すると、その「少し」の閾値が低すぎる。

```console
$ ajisai contract t.ajisai --json     # 4 語を定義したファイル
DOUBLE-ALL | ( 2 -- 1 ) | pure | non-deterministic | space:unbounded | steps/numeric/collection すべて unbounded
TOTAL      | ( 1 -- 1 ) | pure | deterministic     | space:linear    | const / linear / const
F          | ( 1 -- 1 ) | pure | deterministic     | space:linear    | const / linear / const
TEN        | ( 0 -- 2 ) | pure | deterministic     | space:const     | const / const  / const
```

`{ 2 MUL } MAP` という、Ajisai でもっとも自然な一行が、コスト三軸すべて
`unbounded`、空間 `unbounded`、決定性 `non-deterministic` になる。
契約が最も欲しい場所で契約が何も言わない。

### 提案 1 — ブロックを「第一級の契約値」として扱う（★最優先・層 0 の修正と同時設計）

`SpaceSim::Slot` は現在 `{ lit, input, size }` の三点しか持たない。ここに
**「このスロットはコードブロックであり、その契約はこれである」**を持たせる。

```rust
struct Slot {
    lit: bool,
    input: bool,
    size: SpaceClass,
    block: Option<Arc<WordContract>>,   // 追加
}
```

`{ ... }` に入ったら走査を「そのブロック自身の契約推論」に切り替え、
閉じたところで **1 個の Slot を積む**（層 0 のバグはこれで同時に閉じる）。
`MAP` / `FILTER` / `FOLD` / `ANY` / `ALL` / `EXEC` / `COND` は、
オペランド Slot が `block: Some(c)` を持つとき、自分の類を
`c` から合成できるようになる。

- `MAP`: `steps = |input| × c.steps`、つまり `c.steps == Const` なら `Linear`。
- `FILTER` / `ANY` / `ALL`: 同上（短絡は上界を緩めない）。
- `FOLD`: 同上に累算子の成長を join。
- `EXEC`: そのまま `c`。
- `COND`: 全節の join。

**得られるもの**: `{ 2 MUL } MAP` が `steps=linear numeric=linear collection=linear`
になる。現在 `unbounded` に潰れているコードの大半が、実際に宣言可能な数字を持つ。

**なぜ AI 的か**: 人間はこれを「MAP は上界を出せない」と読んで諦める。
機械にとっては、ブロックは既に `WordContract` を計算できる対象であり、
それを Slot に載せないのは単に情報を捨てているだけである。
`purity` は既に `Conditional → Pure`（ブロックの効果は走査が拾う）という
合成規則を持っているのだから、同じ規則を残り 5 軸に適用しないことに理由がない。

### 提案 2 — 再帰に Kleene 不動点を回す

現在、再帰・相互再帰は `GapCode::RecursiveDependency` で即座に
`WordContract::conservative()`（全軸最悪）になる。

しかし推論の値域は**有限束**である。`ContractFlow` は `Fixed{u16,u16}`（高さに
飽和上限を置けば有限）か `Dynamic`、`ContractPurity` は 3 値、`NilBehavior` は 5 値、
`SpaceClass` / `CostClass` は各 4 値、`ContractDeterminism` / `OrderSensitivity` は
各 2 値。すべて単調な join を持つ。**有限束上の単調関数の最小不動点は、
最悪でも束の高さ回の反復で必ず止まる。**

したがって再帰群（依存グラフの強連結成分）に対して、

1. 全メンバを束の底（`WordContract::identity`）で初期化し、
2. 現在の見積もりを使って本体を一巡走査し、
3. 変化がなくなるまで繰り返す（各軸が単調に上がるだけなので停止は保証）、

とすればよい。`word_contract.rs` は既に SCC を意識した構造
（`visiting: HashSet`、`word_identity.rs` の「再帰群を単位でハッシュする」設計）
を持っているので、置き場所はある。

**得られるもの**: `gap.recursiveDependency` の大半が消える。階乗・畳み込み・
木の走査といった、契約を最も検証したい語がまさにここにいる。

**なぜ AI 的か**: 「再帰は静的に無理」は人間の直観であって、束論的には
単なる反復回数の問題である。有限束であることは既に実装が満たしているのに、
その性質が使われていない。

### 提案 3 — Assume–Guarantee：`#:contract` を「仮定」としても読む

現在 `#:contract` は**検査対象**にしかならない。これを、依存語の推論が
届かないときの**仮定**としても使えるようにする。

```
#:contract HELPER ( 1 -- 1 ) pure cost steps=const     # HELPER は別ファイル/未解決
#:contract MAIN   ( 1 -- 1 ) pure cost steps=linear    # HELPER の仮定の下で検証可能
```

結果は三分法のまま、ただし `value` に**仮定集合**を添える:

```json
{ "word": "MAIN", "outcome": "value", "assuming": ["HELPER"] }
```

**得られるもの**: 「検証不能」が終着点ではなくなる。エージェントは
`gapSummary` を見て「HELPER に契約を書けば MAIN が検証できる」という
**次の一手**を機械的に導ける。証明が一発勝負ではなく、
**債務グラフを削っていく作業**になる。これは agent loop と相性が極めてよい。

**なぜ AI 的か**: 人間は「証明できないなら書かない」を選びがちだが、
エージェントは債務が明示されていれば単調に減らせる。
`gap ID`（Phase 3）は既に「測れる負債」を作った。次は**返済経路**を作る番。

### 提案 4 — 決定性軸の非対称を直す

`spec/words.json` で `determinism: stateRelative` は
`MAP FILTER FOLD ANY ALL EXEC VENT KEEP BIND DEF DEL` の 11 語。
`From<Determinism> for ContractDeterminism` はこれを無条件に
`NonDeterministic` に落とす。

一方すぐ上の `From<Purity>` は `Conditional → Pure` にして、
「ブロックの効果は走査が拾うので二重計上になる」と**明示的にコメントしている**。
同じファイル、同じ論拠、正反対の扱い。これは設計判断ではなく非対称の残骸に見える。

結果として `{ 2 MUL } MAP` を含むだけで、純粋・全域・例外なしの語が
`non-deterministic` になる。決定性は観測ダイジェスト（Phase 1）と
計算証明書（後述・提案 11）の土台なので、ここが潰れていると上が建たない。

提案 1 を入れれば `Conditional` 相当の決定性クラスを正しく合成できる。

## 3. 層 2 — 意味論をデータとして出荷する

ここからが本題であり、他言語が構造的に真似できない領域である。

### 3.1 測定：Ajisai の意味論表面はきわめて疎である

`docs/semantics-table.json`（Phase 2 の全数表、61 語 × 入力ドメイン組）の内訳:

| 結果 | セル数 | 割合 |
| --- | ---: | ---: |
| `value` | 178 | **10.8 %** |
| `nil:*` | 306 | 18.6 % |
| `error:*` | 1,157 | 70.5 % |
| **合計** | **1,641** | 100 % |

**well-formed な語適用のうち、値を返すのは 11 語に 1 つしかない。**

この数字は、LLM が Ajisai を「なんとなく」書いたときの成功率の上界そのものである。
そして同時に、**その 10.8 % がどこにあるかは完全に列挙済みで、既に repo に
コミットされている**。使わない手はない。

### 提案 5 — `spec/decoding-automaton.json`：制約付きデコード面（★本書の中核）

Ajisai の well-formedness は**小さなスタックオートマトンで完全に決まる**。

- 語彙は 65 語で閉じている（import も名前空間もない）。
- 65 語中 60 語がアリティ固定。可変は `COLLECT` / `COND` / `VENT` / `KEEP` の 4 つ
  と、`1->variable` の 1 語だけ。
- 構文は `[ ]` / `{ }` / `'...'` / `|` / `^` / 改行 のみ。文脈自由ですらなく、
  深さカウンタ 2 本で足りる。
- 値ドメインは 6 種。全数表がドメイン組ごとの結果を既に持っている。

したがって、**「現在のスタック形状から、次に置ける語の集合」は計算可能**である。
これを機械可読な遷移関係として出荷する:

```json
{
  "schemaVersion": 1,
  "states": { "stackShape": ["scalar","boolean","string","vector","nil","codeblock"] },
  "transitions": [
    { "word": "ADD", "requires": ["scalar","scalar"], "yields": "scalar", "outcome": "value" },
    { "word": "ADD", "requires": ["scalar","nil"],    "yields": "nil",    "outcome": "nil:literal" },
    { "word": "ADD", "requires": ["scalar","string"],                     "outcome": "error:valueShape" }
  ],
  "structural": { "vectorOpen": "[", "blockOpen": "{", "maxVectorDepth": null }
}
```

さらに CLI 側に一手:

```console
$ ajisai next --state '<スタック形状>' --json
{ "legal": ["ADD","SUB","MUL","DIV","EQ",...], "illegal": {"CHARS":"error:valueShape", ...} }
```

**得られるもの**: これは logit mask である。
llguidance / outlines / xgrammar のような制約付きデコーダにそのまま食わせられる。
食わせた瞬間、**LLM は構文エラーも形状エラーも物理的に出力できなくなる**。
`error:valueShape`（794 セル、全体の 48 %）と
`error:typoOrUnknownName`（60 セル）が、生成時点で到達不能になる。

なお `error:typoOrUnknownName` は「語彙が 65 語で閉じている」ことの帰結として
自明に消える。他言語ではこれが不可能なのは、語彙が無限（ユーザ定義・import）
だからである。Ajisai は平坦辞書と Core 封印を選んだ結果、**この一点だけで
他のどの言語よりも制約付きデコードに適した唯一の言語**になっている。
その優位が、まだ現金化されていない。

**なぜ AI 的か**: 人間は言語仕様を「読んで従うもの」と考える。
機械にとって仕様は**サンプリング時の制約行列**である。
「読みやすい仕様」を極めても人間の理解しか改善しないが、
「マスクできる仕様」は生成の誤り率をゼロにする。
そして Ajisai は、その変換が実際に完了できる希少な規模にある。

**現金化の副産物**: このオートマトンは `words.json` と `semantics-table.json` から
**生成できる**（`scripts/generate-decoding-automaton.mjs`）。新しい正典を作らない
——既存の正典の射影である。`--check` を CI に入れれば陳腐化もしない。

### 提案 6 — 観測スペクトル：**振る舞いによる同一性**

Phase 1 の観測ダイジェストは「ある一回の実行」を 32 バイトに畳む。
これを一段上げる。

語 `W` に対し、**正典由来の決定的な入力バッテリ**（全数表のドメイン代表値と、
そこから生成した少数の追加値）を順に与え、各実行の観測ダイジェストを順に
畳んだものを `W` の **観測スペクトル** と定義する。

```json
{ "word": "MY-SUM", "spectrum": "#3f9c...", "battery": "battery-v1", "cells": 24 }
```

これが成立するのは、Ajisai が

- 厳密数（浮動小数の揺れがない）
- 決定的（`PRINT` すら決定的な行列を返す）
- I/O なし・隠れ状態なし
- 全域比較（すべての比較が有限時間で決まる）
- 内容アドレス同一性（辞書の状態が digest で表現できる）

をすべて同時に満たすからである。**このうち一つでも欠けると、
スペクトルは再現しない。** 他言語がこれを持てない理由がここにある。

**得られるもの（すべてエージェント向け）**:

1. **重複検出**: 「あなたが今書いた `MY-SUM` は Core の `SUM` とスペクトルが
   一致する。定義せず `SUM` を使え。」——語彙の肥大化を機械が止める。
2. **リファクタ証明書**: 書き換え前後のスペクトルが一致すれば、
   バッテリ上で観測不能な変更であったことが機械的に言える。
   契約が「型」を保証するのに対し、スペクトルは「振る舞い」を保証する。
3. **振る舞いによる検索**: 「入力 `[1 2 3]` に `[1 3 6]` を返す語はあるか」に
   答えられる。名前を知らないエージェントにとって、これは
   `LOOKUP` より遥かに有用な入口である。

スペクトルは**証明ではない**（バッテリ外の振る舞いは何も言わない）。
それは Ajisai が既に持つ用語で正直に言える: スペクトル一致は `value` ではなく、
理由付きの `nil`——「バッテリ上は区別できなかった」——として報告すればよい。

### 提案 7 — `ajisai diff`：機械可読な意味論変更履歴

全数表と観測スペクトルがあれば、**言語自身の変更が diff 可能な対象になる**。

```console
$ ajisai diff --semantics <commitA> <commitB> --json
{
  "cellsChanged": [
    { "word": "JOIN", "inputs": ["vector","nil"], "from": "error:valueShape", "to": "nil:literal" }
  ],
  "wordsAdded": [], "wordsRemoved": [],
  "identityChanged": ["MY-HELPER"]
}
```

**得られるもの**: 「この PR は意味論を変えたか」が、レビュアの読解ではなく
1,641 セルの差分で答えられる。beta の互換性方針（「一つの現行フォーマット、
変換器なし」）は、この差分がゼロであることの機械的な言明として表現できる。

**なぜ AI 的か**: 人間のレビュアは意味論変更を「気づく」ことしかできない。
セル単位の全数差分は、気づきを網羅性に置き換える。
言語の CHANGELOG が散文をやめてデータになる。

## 4. 層 3 — エージェントのループを閉じる

Ajisai は既に MCP サーバと repair-rate 評価器（`tools/mcp-server/score-repairs.js`）
を持っている。エージェントの修復成功率を測っている言語は他にほぼない。
測っているなら、次は**測定対象そのものを短縮する**番である。

### 提案 8 — 検証済み修復候補（verified repair）

現在、診断は `nextChecks`（人間向けの確認手順テキスト）を返す。
エージェントはそれを読んで書き直し、もう一度投げる——**必ず 2 往復**になる。

Ajisai の実行は純粋・決定的・I/O なし・step limit 付きで、
プログラムは通常数十トークンである。**エンジン自身が候補修復を試して、
成功したものだけを返せる。**

```json
"repairs": [
  { "kind": "typo",        "patch": "AD -> ADD", "source": "1 2 ADD",
    "verified": true, "observationDigest": "#a1b2...", "stackDisplay": ["3/1"] }
]
```

候補の生成規則は既存資産で足りる: `word_candidates.rs` の編集距離候補、
スタック不足に対する `^`（VENT）挿入、`nil` 到達に対する fallback 挿入、
未閉じ区切りの補完。生成した候補を**極小予算で実際に実行し、
成功した候補だけを出す**。推測は一つも出さない。

**得られるもの**: agent loop が 2 往復から 1 往復になる。
`eval:mcp-repairs` は既にこの効果を測る器を持っている。
そして重要なのは、**これが安全に成り立つ言語がほとんどない**ことである。
副作用を持つ言語では「とりあえず実行してみる」ができない。
Ajisai は設計上できる。

### 提案 9 — 反例の最小化（minimal witness）

契約違反が `error` になったとき、現在返るのはメッセージだけである。
**その違反を実際に起こす最小の入力プログラムを添える。**

```json
{ "word": "F", "outcome": "error",
  "witness": { "source": "[ 1 2 ] F", "observation": "error:valueShape" } }
```

コスト軸なら逆向きに: `cost steps=unbounded` と推論したなら、
**その上界を実際に達成する入力族**を示す（`[ 0 N ] RANGE F` で
`N` に対し steps が線形を超える、など）。示せないなら `exact = false`
なのだから、それは `note` であるべきで、両者が構造的に一致する。

**なぜ AI 的か**: 「証明の失敗」は人間には不安だが、機械には**実行可能な
反例**であれば単なるテストケースである。エージェントは反例を回帰テストに
昇格させられる。証明できない箇所が、そのまま corpus の成長点になる。

### 提案 10 — `error:unknown` 303 セルを閉じる（測れる診断負債）

全数表の 1,641 セル中 **303 セル（18.5 %）が `error:unknown`** である。
安定した category id を持たないエラーが、表面の 5 分の 1 近くを占めている。

```
FOLD 144, MAP 24, FILTER 24, ANY 24, ALL 24, TOKENIZE 24,
RANGE 5, CHARS/JOIN/TRIM/NUM/DEF/REFLECT 各 4, FLOOR/ROUND/NEG 各 3, DEL 1
```

`gap ID`（Phase 3）が「検証不能」に安定 id を与えたのとまったく同じ理屈が、
ここにも要る。エージェントは `message` では分岐できない（言い換えで壊れる）。
`error:unknown` のセルでは、エージェントは何も学習できない。

高階語（FOLD/MAP/FILTER/ANY/ALL）に集中しているのは偶然ではない。
**ブロック契約違反（`blockContractViolation`）が category に落ちていない**の
だろう。提案 1 でブロック契約を持つようになれば、ここに正しい id を与えられる。
303 → 0 は、進捗が数値で見える珍しい種類の負債である。

## 5. 層 4 — 計算そのものを証明書にする

### 提案 11 — 計算証明書（computation receipt）

Phase 1 の観測ダイジェスト、Phase 5 のコスト契約、内容アドレス辞書、
決定的実行。この 4 つが揃うと、**一回の計算をそのまま検証可能な証明書に
できる**。

```json
{
  "receipt": 1,
  "sourceDigest":      "#...",
  "dictionaryDigest":  "#...",
  "limits":            { "executionSteps": 1000000, "numericWork": 10000000, ... },
  "contract":          { "outcome": "value", "cost": { "steps": "linear" } },
  "observationDigest": "#b8a752...",
  "resourceUsage":     { "executionSteps": 105, "numericWork": 202, "collectionWork": 1717 }
}
```

意味はこうである。

> 「この辞書状態のもとで、このソースを、この上限で走らせると、
> ちょうどこの観測が出る。事前検査ではコストは線形以下だった。
> 実際の消費はこれだった。」

そして**誰でも再実行して照合できる**。信頼ではなく検証で成り立つ。

**得られるもの（マルチエージェント時代の本命）**:

- エージェント A が計算をエージェント B に委譲し、B の証明書を A が検証する。
  再実行してもよいし、コスト上限だけ見て受け入れてもよい。
- キャッシュが健全になる: `(sourceDigest, dictionaryDigest, limits)` が同じなら
  `observationDigest` は必ず同じ。キャッシュヒットが**証明**になる。
- 事前契約（`cost steps=linear`）と事後実測（`resourceUsage`）が同じ証明書に
  並ぶので、**契約が守られたかどうか自体が監査可能**になる。

Phase 5 が「静的に何を約束したか」を作った。証明書は「約束と実測を
一枚の紙に並べる」段階である。素材はすべて既に実装済みで、
足りないのは**それらを一つの封筒に入れて名前を付けること**だけである。

### 提案 12 — 辞書の Merkle 化と差分同期

`word_identity.rs` は既に「本体と依存の同一性から digest を作る」を実装している。
辞書全体をその上の Merkle 木にすれば、

- 辞書全体の状態が一個の root digest で表現できる（証明書の
  `dictionaryDigest` はこれ）、
- エージェントとホストの間で「私は root `#abc` を持っている」と言うだけで
  **差分だけを同期**できる、
- 語の再定義が波及した範囲が、木の書き換え経路として正確に出る
  （現在も「依存が変わると下流の同一性が変わる」は成立しているが、
  それを**問い合わせられる形**にはなっていない）。

これは新しい概念を足さない。既にある内容アドレス性を、
**問い合わせ可能な構造**にするだけである。

## 6. やらないほうがよいこと

対称性のために明記する。以下は「強みを研ぐ」に見えて、実は薄める。

- **語を足す。** 65 語・36 語 Semantic Kernel という数字は、
  全数表・制約デコード・スペクトルのすべての前提である。語を足すと
  全数表のセル数が伸び、10.8 % がさらに薄まり、オートマトンが太る。
  **語彙の閉性こそが提案 5・6・7 の原資**である。
- **性能を主戦場にする。** 厳密有理数と代数的数を持つ以上、
  素朴なベンチマークで浮動小数点言語に勝つことはない。勝ち筋は
  「同じ答えが二度出ること」であって「速く出ること」ではない。
- **型注釈の構文を足す。** `#:contract` はコメントであり、
  言語意味論に一切触れないという規律が、10 概念という同一性を守っている。
  推論を強くする（層 1）ほうが、構文を足すより常に安い。
- **散文ドキュメントを増やす。** 本書を含めて、`docs/dev/` の文書は
  人間の理解しか改善しない。**生成物 + `--check` に落とせるものは、
  文章にせずスクリプトにする**のが、この repo が既に選んでいる規律である。
