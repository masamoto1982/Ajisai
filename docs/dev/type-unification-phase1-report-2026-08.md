## 1. 実装した内容（(A) 案、指示書 §2.1）

### 1.1 表現

`ValueData::CodeBlock(Vec<Token>)` を削除し、`ValueData::Symbol(Arc<str>)` を
追加した。六つの互いに素な領域という数は変わらない（`CodeBlock` が抜けて
`Symbol` が入るので 6 → 6。Phase 0 報告 §7-3 が指摘したとおり、指示書 §2.4 の
「五つになる」という記述は誤りだった）。

### 1.2 リテラル構築の統合

`[ ]` と `{ }` は同一のビルダー（`vector_literal.rs`、
`collect_bracketed_with_depth` に改名）で構築するようにした。両者は
どちらの綴りで開かれたかを問わず同一の値を作る——裸の名前は
（`TRUE`/`FALSE`/`NIL` を除き）`Symbol` になる。これにより
`LANG.VALUES.VECTOR` の「Vector リテラル中の裸の名前は自分自身のテキスト」
という規定は、`Symbol` を経由した「自分自身の指示対象」という規定に変わる。

実測：

```
{ 1 2 + } [ 1 2 + ] EQ     => TRUE   （指示書冒頭の動機づけ例、そのまま成立）
[ FOO ]                    => [ FOO ]        (旧: [ 'FOO' ])
{ 1 2 ADD }                => [ 1/1 2/1 ADD ]（旧: { 1 2 ADD } のまま）
{ 1 2 ADD } EXEC           => 3/1
[ 1 2 ADD ] EXEC           => 3/1
```

開いた綴り（`[`/`{`）は自分自身の閉じ（`]`/`}`）を要求する字句上の制約は
残した——これは値の意味論には現れない、パーサ側の便宜として残せる
（§3 で述べる `COND` の一部修正がこれに依存している）。

### 1.3 実行系の橋渡し（`value_as_code.rs`、新規）

`EXEC`・`PROBE`・`DEF` の本体・高階語（`MAP`/`FILTER`/`FOLD`/`ANY`/`ALL`）は、
いずれも「Vector の要素を命令列として解釈する」経路を必要とする。これを
指示書 §2.1(A) が示唆した「実行エンジンに新しい経路を設ける」を文字通り
再実装する代わりに、**Vector の要素を `Vec<Token>` に変換し直し、既存の
Token ベースの実行ループ（`execute_nested_block` 等）へ橋渡しする**という
縮小策で実装した。これはスパイクとしての意図的な妥協であり、Phase 2 の
提案ではない——既存の末尾呼び最適化・`KEEP` 処理・エラー診断コンテキストを
無傷で再利用できる代わりに、次の代償を払う：

- リテラルの元の字句（レクセム）は保存されない。`1.0` として書かれた
  Scalar は `1` として再合成される（数値としては同じだが、字句としては別物）。
- `ExactScalar`（`SQRT` 等、実行時にしか生じない）には対応する数値リテラルの
  綴りが存在しないため、橋渡しはエラーになる。これは統合の要件ではなく、
  この橋渡し実装固有の穴である。

### 1.4 `REFLECT` を恒等写像にした（指示書 §3.1-3）

`REFLECT` は削除せず、恒等写像として辞書に残した（削除するかテストとして
残すかは Phase 1 の判断に委ねられていた——本書は前者寄りの中間案を採り、
「まだ `REFLECT` という語は存在するが何もしない」状態にして、conformance の
`reflection-*` 群が**どのアサーションで**壊れるかを実測することを優先した）。

### 1.5 `COND` の部分修正（§3 で詳述）

`COND` の節ブロック発見ロジックは、統合前は「トップから
`ValueData::CodeBlock` である限りポップし続ける」という実行時の領域判定
だった。統合後はこれが意味をなさない（あらゆる Vector が該当してしまう）。
コンパイル済み経路（`op_cond_dispatch`）は、コンパイル時に判明している
節の個数を直接使うことで実行時判定を迂回できたが、動的（非コンパイル）
経路（`op_cond`）にはそれに代わる位置情報が存在せず、実装を断念して
明示的なエラーを返すようにした（詳細と実測は §3）。

### 3.3 `REFLECT` の恒等化により意味を失った（11 件）

Vector リテラル構築が辞書状態を見ない以上、`REFLECT` の有無に関わらず
両辺は同じ `Symbol` を含む同じ値になるため成立する。**Phase 0 の机上分類は
この 2 件を数え過ぎていた**——本書はこの誤差を訂正する。

### 3.4 `COND` の構造的な壁（8 件、Phase 0 未発見）

これが Phase 1 で最も重い発見である。指示書 §5.3（本書執筆前に「高階語の
被演算子判別」として言及されていた懸念）よりも根が深く、**`MAP`/`FILTER`/
`FOLD`/`ANY`/`ALL` は実際には問題なく動いた**（スタック上の位置——
末尾がコード、その下が対象——で被演算子を判別する既存の規約がそのまま
機能した）。壁は `COND` 固有だった。

非通過の 8 件：

| id | エラー |
| --- | --- |
| `core-cond-truthy-number-guard` | 「動的 COND の節ブロック発見に代わる手段がない」という明示エラー |
| `core-cond-idle-fires-in-written-order` | 同上 |
| `core-cond-clause-above-idle-wins` | 同上 |
| `core-cond-one-line-is-the-same-program` | 同上 |
| `core-word-body-multi-line-cond` | `'\|' separator is only valid directly inside a code block` |
| `core-self-recursion-through-map-block` | 同上 |
| `core-self-recursion-through-exec-block` | 同上 |
| `core-self-recursion-through-filter-block` | 同上 |

**なぜ `COND` だけが特別に壊れるか。** `[ 1 2 ] { 2 MUL } MAP` のような
高階語は、被演算子が「ちょうど二つ、スタック上の決まった位置」という
固定の形をしている——位置だけで足りる。`COND` はこれと違い、
`{ guard1 | body1 } { guard2 | body2 } ... COND` という**可変長の節ブロック
の連なり**を扱う。統合前は「スタックの上から `ValueData::CodeBlock` で
ある限りポップし続ける」という実行時の領域判定でこの可変長を発見していた
——これは**位置に代わる情報が存在しない、真に領域判定でしか解けない
問題**であり、指示書 §2.1 が想定していなかった追加コストである。

二つの独立した経路でこれを確認した：

1. **コンパイル済み経路（`op_cond_dispatch`）は部分的に救済できる。**
   `COND` の直前に連続する `{ }`-綴りの `PushCodeBlock` コンパイル済み命令の
   本数は、字句レベル（ソーステキストのどちらの綴りを使ったか）で
   コンパイル時に決まる——この情報は値がいったん構築されて綴りの区別が
   失われる**前**に確定するので、実行時にポップする個数をコンパイル時の
   節数から直接計算すればよく、領域判定は不要になる。これを実装し、
   単体では動作を確認した。
2. **動的（非コンパイル）経路（`op_cond`）には代替がない。** トップレベルの
   プログラム文（`ajisai run` が直接実行する裸のプログラム文——DEF で
   包まれていないもの）は、この Phase 1 の実装ではコンパイル経路を
   通らない（コンパイルは DEF された Word の本体にのみ適用される）。
   conformance ケースの `ajisai-source` は大半が裸のトップレベル文であり、
   これらは 1 の救済の恩恵を受けない。実測では 4 件がこの動的経路の
   「代替手段がない」エラーに直接到達した。

さらに、**残り 4 件は 1 の救済そのものが壊れる別の理由**で失敗した。
`{ ... { 2 LT | 1 * } { IDLE | [ 1 2 ] - { FIB } MAP 0 { + } FOLD } COND
} 'FIB' DEF` のように、`COND` が `DEF` された Word の本体の**内側**に
ネストして書かれている場合、`DEF` はその Word 本体全体を一度 Vector の
要素列として構築し、実行のために `value_as_code.rs` の橋渡しで字句へ戻す
（§1.3）。この橋渡しは、ネストした節ブロック（`{ 2 LT | 1 * }`）を
**常に `Token::VectorStart`/`VectorEnd` で再合成する**——値がいったん
`Value::Vector` になった時点で、それが元々 `{` で書かれたのか `[` で
書かれたのか、という情報は（統合の目的どおり）消えているからである。
一方、`\|` の妥当性を検査する `tokenizer::validate_code_tokens` は、
「直近の開きが `Token::BlockStart` であること」を要求する——**この検査
自体が、統合によって値から失われるはずの綴りの区別に、まだ依存している**。

つまり `COND` は二重に壊れている。動的経路の領域判定（1）と、
`\|` の妥当性検査（2）は、**どちらも「値がいったん構築された後も、
元の綴りがどちらだったかを知る必要がある」という、統合の理念と直接
衝突する前提**を持っている。これは指示書 §2.2 が契約推論エンジンについて
立てた「増分か作り直しか」という問いと同じ形の問いを、`COND` という
別の場所に対して投げかける——**そして実測は「増分では埋まらない」side
であることを示した**。コンパイル時点の字句情報を保持する部分修正
（1）はしのげたが、それは「まだ値になっていない」間だけ有効な回避策で
あり、値が一度構築されてから字句へ戻す必要がある経路（DEF された Word
本体、§1.3 の橋渡し）には効かない。

## 4. Reference の可読性判定（指示書 §3.1-6）

`public/docs/index.html` の「Code as data」節（`{ }` の表示規約を説明する
箇所）は、統合後の実際の描画と**直接矛盾する**具体例を持っていた。

> 「コードブロックがスタック上にあるとき、それが書かれたとおりのソース
> ——波括弧込みで——を表示する。`{ 2 MUL }` のように」

実測：

```
{ 2 MUL }   =>  [ 2/1 MUL ]
{ }         =>  [ ]
```

本書の実装は「Vector 領域の値はすべて `[ ]` で統一して描画する」という
選択をした（§1.2）。これは Phase 1 の実装判断であって正典の決定ではないが、
**この選択の帰結として、`{ }` で書いたものが `[ ]` で表示されて返ってくる、
という往復の不一致が生じる**——ユーザが打った綴りと、値が表示に戻ってくる
綴りが一致しない。これは読みにくさの実例として実際に観測された、
原提案 §6 が「結論を持たない」とした論点への直接の材料である。

もう一つの選択肢（表示側で「どちらの綴りで構築されたか」のヒントを
保持し、`{ }` 由来の値は `{ }` で、`[ ]` 由来の値は `[ ]` で描画する）
も考えられるが、これは Phase 0 報告 §5.1 が既に指摘した「表示が単射で
ない」問題を、統合後の世界に**そのまま持ち越す**ことになる——`EQ` が
`TRUE` を返す二つの値が異なる綴りで表示される、という新しい形の不一致に
すり替わるだけである。どちらの描画方針を採っても、「両方の綴りが同じ
値を指す」という統合の主張と、「打った通りに表示される」という
読みやすさの直感は、完全には両立しない。これは Phase 1 が実測で
確認した、原提案 §6 の論点に対する具体的な材料である。

## 5. Phase 0 が見積もっていなかった新発見

### 5.1 `Tensor` 最適化への波及（§1.3 実装中に発見）

`[ 1 2 ]` のような、要素がすべて数値で矩形をなす Vector リテラルは、
既存の最適化により構築時に `ValueData::Vector` ではなく
`ValueData::Tensor`（密な数値ストレージ）へ自動的に昇格する
（`Value::from_vector_promoted`、統合以前から存在する挙動）。

`EXEC` の初版パッチは `Value::as_vector()`（`Vector` のみを認識し、
`Tensor` を除外する）を使っていたため、**`[ 1 2 ADD ] EXEC` は成功するが
`[ 1 2 ] EXEC` は失敗する**という非一貫な挙動を生んだ——前者は `ADD` と
いう `Symbol` を含むため `Tensor` に昇格せず `Vector` のまま残るが、
後者は純粋な数値のみなので `Tensor` に昇格してしまうためである。
`Value::as_vector_view()`（`Vector` と `Tensor` を統一的に扱う、既存の
別のアクセサ）に切り替えて解消した。

指示書にも原提案にも Tensor への言及はなく、Phase 0 の実測にも現れて
いない。**統合の対象が「Vector」であるとき、それは表面上の値領域の話で
あって、内部表現が二種類（`Vector`/`Tensor`）に分かれていることは、
実行系の橋渡しを書いて初めて表面化した**——これは Phase 0 §2.1 の
「内部表現は観測不能」という前提（`LANG.VALUES.DENOTATION`）が、
実装レベルでは決して自明でないことの一例でもある。

### 5.2 `Token::CondClauseSep`（`\|`）も昇格が要る（§3.4 で発見）

指示書 §2.1(A) は `Value::Symbol` の追加だけを挙げていたが、実際には
`{ IDLE | 1 }` のような節ブロックリテラルを統合後の即時構築方式で
扱うには、`\|` トークンにも何らかのデータ表現が要る——統合前は `{ }`
の中身が実行時まで生のトークン列のまま保持されていたため、`\|` の
特別な意味は「実行されるときだけ」意識すればよかったが、統合後は
`{ }` もリテラル構築の時点で即座に値へ評価されるため、`\|` に
出会った瞬間に「これは何を表す値か」を決めなければならない。

本書の実装は `Symbol("|")` として仮に扱い、実行系への橋渡し時に
`Token::CondClauseSep` へ戻す、という対症療法で通した。これは §3.4 で
述べた `COND` の構造的な壁の**一因**であり、単独では解決していない。

### 5.3 `kernel::value::KernelValue` という第二の並行表現（§1 の実装中に発見）

`rust/src/kernel/legacy_adapter.rs` は、`ValueData`（本書が変更した表現）
とは別に、`KernelValue`（`rust/src/kernel/value.rs`、Semantic Spine
移行計画の一部）という**もう一つの、独立した値表現**を橋渡ししている。
この `KernelValue` にも独自の `CodeBlock` variant があり、本書の変更の
影響を受けてコンパイルエラーになった。

このモジュール自身のドキュメントコメントに「Phase 2 導入時点では、
どの実行経路もこの橋渡しを呼ばない」と明記されている——**現時点では
死んでいるコードである**。今回は最小限（1 トークンの `CodeBlock` として
場当たり的に往復させる）で通した。

これは Phase 0 のどの実測にも現れなかった、**改修Ⅰの影響範囲が
`ValueData`／`Token` の外側、`kernel::value::KernelValue` という
第二の値表現の設計にまで及ぶ**ことを示す発見である。現状は死んでいる
コードなので実害はないが、Semantic Spine 移行が実際に稼働経路へ
接続された場合、この橋渡しは本書の場当たり的な処置では済まなくなる。

## 6. 総括と推奨

**測定できたこと（成功）：**

- (A) 案は構文的に構築可能である。`{ 1 2 + } [ 1 2 + ] EQ` は `TRUE` になり、
  `EXEC` はどちらの綴りでも動く——指示書 §1 の動機は実装で再現できた。
- 契約推論エンジン（`word_contract.rs` 系）は、ブラケットのトークン自体を
  残す限り、統合の影響をほとんど受けない。指示書 §2.2 の懸念は実測では
  的中しなかった。
- conformance の非通過数（23/279）は Phase 0 の机上見積もり（22 件）と
  ほぼ一致し、Phase 0 の分類方法の信頼性を裏づけた。

**測定できたこと（新しい懸念）：**

- `COND` の節ブロック発見は、統合と本質的に相容れない仕組みで動いている。
  部分修正（コンパイル時の字句情報を使う）はしのげるが、値が一度構築
  されてから字句へ戻される経路（`DEF` された Word 本体）には効かない。
  これは「増分では埋まらない」種類の壁であり、指示書 §0.4 第三条件が
  契約推論エンジンについて懸念したのと同じ性質の壁が、別の場所
  （`COND`）に実在することを実測で確認した。
- 実行系の橋渡し（本書の実装方式）は、レクセム保存を失い、`ExactScalar`
  を実行できず、`Tensor` 最適化・`\|` トークン・第二の値表現
  （`KernelValue`）という、指示書のどこにも書かれていなかった三つの
  追加箇所に触れる必要があった。

**推奨（決定ではない）：**

本書は Phase 2 に進めるべきかどうかの決定を下す文書ではない
（指示書 §3.2 のとおり、決定は人間が行う）。実測に基づいて言えることは：

1. **表現の統合そのもの（(A) 案の骨格）は実装可能で、コストは Phase 0
   の見積もりの範囲に収まっている。**
2. **`COND` の再設計は、Phase 2 に進むなら避けて通れない、独立した設計
   課題である。**本書の場当たり的な部分修正では実運用に耐えない
   （動的経路が丸ごと使えない状態のままでは、`DEF` された Word の中で
   `COND` を使うプログラムの大半が壊れる）。この設計課題を Phase 2 の
   スコープに含めるか、`COND` の呼び出し規約自体を作り直す**追加の
   改修**として切り出すかは、Phase 0 報告 §7 の未回答質問（特に
   互換性方針）と合わせて判断が要る。
3. Phase 0 報告 §7 で未回答のままの質問（互換性方針、`{ }`/`[ ]` を
   意味論上どう扱うか）は、本書の実測（§4 の可読性判定、§3.4 の
   `COND` の壁）でむしろ重みを増した——これらへの回答なしに Phase 2 の
   実装範囲を確定することはできない。
