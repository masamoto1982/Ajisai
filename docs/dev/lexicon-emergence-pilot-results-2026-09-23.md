## 3. 仮説ごとの観察

### 3.1 H1（独立到達）— 交絡のため判定不能

| 集合（辞書なし・独立） | 2 体以上が到達した類 | 全員が到達した類 |
| --- | --- | --- |
| solo の 3 体 | 13 / 34 | 6 / 34 |
| bottleneck gen0 の 3 体 | 14 / 34 | 2 / 34 |

辞書なしの 6 体を合わせると、12 類が 4 体以上に到達された。6 体全員が同じ字面
（D0 一致）に到達したのは `' ' TOKENIZE`（語への分割）である。独立到達はこの程度
起こるので、H1 を評価するには指示書 §5.3 の統制（系統の異なるモデルの混在）が
前提になる。同一モデルだけのパイロットで分かるのは、それが前提だということだけである。

### 3.2 H2（構成性）— 兆候のみ

辞書のうち他の辞書語を本体で呼ぶ語の割合は、gen1 が 3/8、gen2 が 4/8 だった。
gen2 の辞書に入った `G1A.RANGE` は、gen0 から継承した `G0B.MAX` と、gen1 で作られた
`G1A.MIN` の合成である。標本が 2 点しかないので、傾向とは言えない。

**継承による忘却と再発明は観察できた。** 容量 8 の外に落ちた語は、次世代の全員が
作り直した。gen1 では 3 体全員の再定義が 8 類（MIN・RANGE・NORMALIZE・STDDEV・CAP・
TITLE・ACRONYM・LONGEST）あったが、MIN と RANGE が辞書に入った gen2 では 3 類
（NORMALIZE・TITLE・ACRONYM）に減った。辞書に入った語は、その後の全被験体が
再定義せずに使った（gen1・gen2 の 6 体全員が継承語を 7〜8 語使用）。

### 3.3 H4（Core の使用頻度）— 課題に強く依存

正答解答から（ユーザー語を展開したうえで）到達された Core 語は 33、未使用は 67 だった。
未使用の大半は、課題に対応する題材がない語（Record 操作、三角関数、NIL 系など）である。
§7.4 の退役候補の列の上位（`LTE` `GTE` `SUB` `CEIL`）では、`SUB` だけが使われた
（60 解答）。この数字は課題族 2 つの選び方で決まるので、退役の根拠には使えない。

### 3.4 H5（監査可能性）— 反例あり

不一致は 21 件で、すべて `stats.deviations` / `stats.variance` / `stats.stddev` の
3 問に集中している。原因は一つで、実測した再現は次のとおり。

| 入力 | 結果 |
| --- | --- |
| `[ 'X' BIND X 1 + ] 'H' DEF [ 3 ] KEEP H` | `[ 3/1 ] [ 4/1 ]` |
| `[ 3 ] [ 'X' BIND X 1 + ] KEEP EXEC` | `[ 3/1 ] 'X' [ 4/1 ]` |
| `[ 3 ] KEEP [ 1 + ] EXEC` | `[ 3/1 ] 1/1 [ 4/1 ]` |
| `[ 3 ] KEEP [ 9 ] +` | `[ 3/1 ] [ 9/1 ] [ 12/1 ]` |

- ユーザー語 H に掛けた `KEEP` は、H の呼び出し全体に掛かる（H が消費した `[ 3 ]` を残す）。
- 同じ本体を `EXEC` で評価すると、`KEEP` はリテラルを飛び越えて、**ブロック内で
  最初に実行される語**に掛かる（`BIND` に掛かれば名前 `'X'` が、`+` に掛かれば `1/1` が残る）。
- したがって「ユーザー語 = その本体」という置換は、`KEEP` の直後では意味を保存しない。
  本道具の展開（`[ body ] EXEC`）は、この位置で別のプログラムを作る。

`KEEP` は短く書けるので `G0B.DEV` は最も使われた偏差の語になり、ボトルネックで
選ばれ、以後の全被験体に継承された。**「方言化しても Core へ機械的に展開して監査
できる」という主張は、現状の意味論では `KEEP` の前で成り立たない**。この観察は
所有者判断へ回す。考えられる方向は、`KEEP` の適用対象を字面で決まるものにする、
ユーザー語のアリティを宣言させて展開を `BIND` 経由で書けるようにする、などである。
正典は変えていない（指示書 §0.4）。

**裁定（2026-09-23）:** 所有者はアリティ宣言の方向を選んだ。実装は
`word-arity-header-work-order-2026-09.md` を参照。見出しを持つ語は `BIND` 経由で忠実に
展開でき、`KEEP` の直後でも意味を保つ。本パイロットの解答は見出しを使っていないので、
§2 の数値は変わらない。

| # | 事実（実測） | 対処 |

| M-1 | `DIGEST` は、`BIND` の名前だけが違う本体を区別する（`'V' BIND …` と `'W' BIND …` で別の値） | D0α を追加した。束縛名を出現順に `_B0, _B1, …` へ改名してからハッシュする。MEAN・MIN・MAX・NORMALIZE などの類は、この段で初めて結合した |

| M-3 | 初版の探針では、語で分割する title-case と文字を走査する title-case（`'x  y'` で前者は ERROR、後者は `'X  Y'`）が D1 で結合した | 探針に `''`・`'x  y'`・`' lead'` を加えた。本書の数値は追加後のもの（類は 33 → 34） |

そのほかの観察:

- 被験体は、束縛名にも自分の接頭辞を付けた（`'G0A.XS' BIND`）。プロンプトの
  「名前は `G0A.` で始めよ」を束縛にも当てはめたと見られる。D0α はこれを吸収する。
- 被験体の `note` は、同じ類の中でほぼ同じ文言だった。

## 5. Phase 2 に進む前に必要な変更

1. **モデル系統の混在（指示書 §5.3）を Phase 2 の必須要件にする。** 同一モデルでは、
   収束の基準線が高すぎて H1 を測れない。
2. **課題を難しくし、一問一語で済まない形にする。** 各問に複数の下位計算の組み合わせを
   要求し、問の数を増やす。正答率と圧縮率に分散が出るようにする。
3. **C-shuffled を実施する。** 継承語の再利用が、名前と `note` の意味に依存しているかを切り分ける。
4. **H5 の展開規則を決める。** §3.4 を所有者が裁定するまで、`KEEP` の直後にユーザー語が
   来る解答は「展開不能」として別に数え、H5 の不一致と混ぜない。
5. 探針集合は今後も観察から拡張しうる。拡張したら、類の数の変化を必ず記録する（M-3）。
