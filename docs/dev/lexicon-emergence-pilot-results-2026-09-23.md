### 3.2 H2（構成性）— 兆候のみ

辞書のうち他の辞書語を本体で呼ぶ語の割合は、gen1 が 3/8、gen2 が 4/8 だった。

### 3.4 H5（監査可能性）— 反例あり

不一致は 21 件で、すべて `stats.deviations` / `stats.variance` / `stats.stddev` の
3 問に集中している。原因は一つで、実測した再現は次のとおり。

| 入力 | 結果 |
| --- | --- |
| `[ 'X' BIND X 1 + ] 'H' DEF [ 3 ] KEEP H` | `[ 3/1 ] [ 4/1 ]` |
| `[ 3 ] [ 'X' BIND X 1 + ] KEEP EXEC` | `[ 3/1 ] 'X' [ 4/1 ]` |
| `[ 3 ] KEEP [ 1 + ] EXEC` | `[ 3/1 ] 1/1 [ 4/1 ]` |
| `[ 3 ] KEEP [ 9 ] +` | `[ 3/1 ] [ 9/1 ] [ 12/1 ]` |

- ユーザー語 H に掛けた `KEEP` は、H の呼び出し全体に掛かる（H が消費した `[ 3 ]` を残す）。
- 同じ本体を `EXEC` で評価すると、`KEEP` はリテラルを飛び越えて、**ブロック内で
  最初に実行される語**に掛かる（`BIND` に掛かれば名前 `'X'` が、`+` に掛かれば `1/1` が残る）。
- したがって「ユーザー語 = その本体」という置換は、`KEEP` の直後では意味を保存しない。
  本道具の展開（`[ body ] EXEC`）は、この位置で別のプログラムを作る。

`KEEP` は短く書けるので `G0B.DEV` は最も使われた偏差の語になり、ボトルネックで
選ばれ、以後の全被験体に継承された。**「方言化しても Core へ機械的に展開して監査
できる」という主張は、現状の意味論では `KEEP` の前で成り立たない**。この観察は
所有者判断へ回す。考えられる方向は、`KEEP` の適用対象を字面で決まるものにする、
ユーザー語のアリティを宣言させて展開を `BIND` 経由で書けるようにする、などである。
正典は変えていない（指示書 §0.4）。

**裁定と撤回（2026-09-23）:** 所有者はいったん、アリティ宣言の方向を選んだ。
定義の先頭に入力の個数を書く「パラメータ見出し」`[ A B | body ]` を PR #1718〜#1720 で導入し、最終的に必須にした。
この導入を、PR #1722 で撤回した。

- 撤回の理由: 効果（監査可能性、計測器の扱いやすさ）は未実測のまま、表面の複雑さだけが確定した。
  - 規則が 1 つ増えた。
  - `|` が予約語になった。
  - 定義の記法が長くなった。
  - 既存の定義との互換性が切れた。
- 撤回後も残したもの（見出しとは独立の、実在したバグの修正 3 件）:
  1. `KEEP EXEC` が、ブロック内で最初に実行される語に漏れていた。`KEEP` が `EXEC` の呼び出しそのものを修飾するように直した（上表 2 行目・3 行目は解消）。
  2. `check` が、`BIND` で作った名前を未知の語として拒否していた。
  3. 契約推論が、`BIND` で作った名前を解決できない語として読んでいた（M-2）。これを「大きさの分からない値 1 つ」として読むように直した。
- `KEEP` の直後: 本体への置換は忠実でない。この事実を仕様に明記した（LANG.MODIFIERS）。Core 語への展開は、`KEEP` の直後にあるユーザー語を置換しない。

**KEEP の廃止（2026-09-24）:** 所有者の判断で、`KEEP` そのものを廃止した（Core は 100 語から 99 語へ）。

- 語はすべて、読んだオペランドを消費する。値を 2 回以上使うときは `BIND` で名前を付けて読む（`5 'N' BIND N N 1 +` → `5 6`）。
- 修飾子がなくなったので、ユーザー語を本体で置き換えても、消費されるオペランドは変わらない。本節の反例は、言語の側で消えた。
- 条項 LANG.MODIFIERS.CONSUMPTION は LANG.STACK.CONSUMPTION に改名した。
- 実装から削除したもの: 消費モード、呼び出しの到達深さの監視、`KEEP` を実行やコンパイルで扱う経路、推論の中の `KEEP` 処理、GUI の「保持」の色分け。
- 上の「残したもの」の 1 番（`KEEP EXEC`）は、対象がなくなったので意味を失った。

## 5. Phase 2 に進む前に必要な変更

1. **モデル系統の混在（指示書 §5.3）を Phase 2 の必須要件にする。** 同一モデルでは、
   収束の基準線が高すぎて H1 を測れない。
2. **課題を難しくし、一問一語で済まない形にする。** 各問に複数の下位計算の組み合わせを
   要求し、問の数を増やす。正答率と圧縮率に分散が出るようにする。
3. **C-shuffled を実施する。** 継承語の再利用が、名前と `note` の意味に依存しているかを切り分ける。
4. **H5 の展開規則。** `KEEP` の直後にユーザー語が来る解答は「展開不能」として別に数え、
   H5 の不一致と混ぜない（§3.4 の裁定と撤回を参照）。
5. 探針集合は今後も観察から拡張しうる。拡張したら、類の数の変化を必ず記録する（M-3）。

**§5.1 一世代の流れ（要点）。** 各被験体は新しい文脈で、生成されたプロンプト 1 通だけを
受け取り、前世代の辞書（容量 K）を継承して課題を解く。世代の終わりに D0/D0α/D1 で
同値類を作り、使用頻度上位 K 語を次世代の辞書にする（`lib/evolve.mjs`）。

**§5.2 条件。** C-bottleneck（K 小、世代交代あり、本条件）、C-open（K 無制限、H2 の対照）、
C-solo（辞書を共有しない。H1 の基準線、独立到達の偶然率）、C-shuffled（辞書の代表名を
無意味な名前に置換。名前の意味に頼った再利用かを切り分ける）。

**§5.3 統制。** 同じモデルの複数体が同じ定義を出すのは事前分布の反映でありうる——最大の
交絡。C-solo の独立到達率を基準線とし H1 はその超過分で評価する。経路 B では世代内に
大・中・小 3 系統のモデルを混ぜ、系統をまたぐ収束を強い証拠とする。生成パラメータを記録し
条件間で揃える。ハーネスがサーバー側の refusal fallback を有効にしないのはこのためである
（fallback はどのモデルが答えたかを変える）。

**§5.4 H5 の検査。** 全解答について辞書語を定義本体で再帰的に置き換えて Core 語だけの
プログラムを作り、元と D1 同値であることを `compute` で確かめる。展開には名前ではなく
ハッシュの対応を使う。一件でも失敗したら解答と辞書の状態を保存して報告する。
