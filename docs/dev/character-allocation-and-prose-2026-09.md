# 字句に文字を取るときの規準——文書側で稼働中の区切り文字は避ける（2026-09-22）

Status: 非正典。正典は `spec/grammar.json`。本書は**ある文字を字句文法に割り当てて
よいかを判断する規準**を記録する。語を採る規則（`vocabulary-100-work-order-2026-09.md`
§7.3）とは別の軸であり、語彙の数の話ではない。

## 0. 規準

ある文字を字句に取る前に、**その文字が Ajisai について書く側で区切りとして
稼働していないか**を見る。稼働しているなら、割り当ては言語の可読性を上げる
代わりに**文書の可読性を下げる**取引になる。

**空いている文字を取るのと、使われている文字を取り上げるのは別の判断である。**
前者は枠の消費、後者は交換であり、交換なら何を失うかを先に言えなければならない。

## 1. なぜ [方針記録]

`ajisai-authoring-style.md` は逆向きの規律を既に持っている——§2「the symbol-as-word
hazard」（`+` `-` `*` `/` のような語のエイリアスは普通の句読点に見える）と §8
「In-cell separators」（表のセル内で複数トークンを区切るとき、Ajisai の字面である
記号を使ってはならない）。同書の結語はこう書く——「Ajisai のコード、その背後の
数学、両者についての散文は、視覚的にも構造的にも区別されていなければならない。
記号が句読点と読み違えられず、演算子が語と読み違えられないために」。

本書はその**対**である。§2・§8 は「散文は言語が使う文字を避けよ」と言う。ここで
言うのは「**言語は散文が使う文字を避けよ**」である。片方だけでは、文字が字句に
取られるたびに散文の側が使える区切りを失っていき、その損失をどこにも記録せずに
済んでしまう。

具体的な損失は3つの形で現れる。

**(a) 検査が例外を必要とする。** Ajisai の読み物は実行で検査される
（`check:reference-samples` は Reference の全サンプルを走らせ、
`generate-skill-md.mjs` は埋め込み断片を CLI に通す）。散文中の断片が「ソース」か
「説明の形」かを機械が判別できないと、検査は例外を持たざるをえない。実例:
SKILL.md §2/§3 の波括弧断片を実行して Record を答えるか検査する規則
（`record-literal-2026-09.md` §5）は、`{ key value … }` のような**図式**を
省略記号で識別して実行から除外している。字句と散文の区切りが重なるほど、
この種の除外が増える。

**(b) `:` は Ajisai 自身の道具立てで稼働している。** `#:contract`（宣言された契約、
`rust/src/agent/contract_decl.rs`）と `#@`（テストディレクティブ）は、どちらも
`#` コメントに続く記号で道具に語りかける形である。字句上は今もコメントの一部だが、
**規約としてはコロンが既に役割を持っている**。

**(c) `label: value` は執筆規約が指定した情報の形である。**
`structured-prose-style.md` は情報の形を「文 / label:value / 表 / 図」から選ぶ規律で、
`label:value` を翻訳に耐える基本形の一つとして名指ししている。Reference の日本語
散文にも全角コロンによる同形が使われている。

## 2. 二つの実例——この規準の由来

| 文字 | 文書側の稼働 | 判断 |
| --- | --- | --- |
| `{` `}` | 無し。`source-character-liberation-2026-09.md` が解放した直後で、散文も表も使っていなかった | **取った**。Record リテラル（`record-literal-2026-09.md`） |
| `:` | 稼働中。(b) と (c) のとおり | **見送った**。所有者の判断 |

`:` を見送った判断には、可読性の得が小さいという事情も重なっている——引用符は
次が空白のときにだけ閉じるので `{ 'x': 1 }` は書けず、得られるのは浮いたコロン
`{ 'x' : 1 }` にとどまる（`record-literal-2026-09.md` §3(a)）。つまり**文書側の
負担を払っても、払った分の形は手に入らない**。この2つが揃ったので見送りになった。

## 3. 規準が言わないこと

- **「よく使われる記号は永久に取れない」ではない。** 取るなら、文書側がその形を
  別の情報形（表・文）へ移せるかを先に問う。移せるなら取ってよい。順序の話である。
- **文書側の稼働だけで決まるのでもない。** 字句規則が別の理由でその形を許さない
  こともある（`:` の場合は文字列の閉じ規則）。両方を見る。
- **文字を取ったあとの規律は変わらない。** `rust/src/surface_forms.rs` の
  `SURFACE_FORMS` に載るのは「語の規則を超えた何かをする」形だけであり、死んだ
  概念名を戻すこととは別である。

## 4. 適用の手順

1. 候補文字を読み物3面（README / Reference / Specification）と生成物
   （SKILL.md、MCP quickstart）で検索し、散文の区切りとして使われているかを見る。
2. 使われていれば、その形を別の情報形へ移せるかを問う。移せないなら見送る。
   移すなら、移動を先に済ませてから割り当てる。
3. 空いていれば、字句規則の側で成立するかを確かめる（whole-lexeme 規則で足りるか、
   per-character 規則が要るか。後者は `spec/grammar.json` が全廃した種類の規則で、
   復活させるなら別の議論になる）。
4. 取った文字は `SURFACE_FORMS` に載せ、`check:grammar` が word manifest と
   突き合わせる。
