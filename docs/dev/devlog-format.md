# 開発ログ（Blogger）執筆規約

Ajisai の大きな改修ごとに Blogger へ残す開発ログ記事の形式。

## 位置づけ

- **非正典。** 本書は記事の書き方の規約であり、言語意味論も互換性方針も定義しない。
  正典は `spec/` 配下の各ソースと、そこから生成される `SPECIFICATION.html` のみ。
- 記事の内容は、当該改修の **PR サマリーの要約** とする。差分そのものを読み直して
  書くのではない。PR サマリーが正確であることが記事の正確さの前提であり、
  両者が食い違ったら PR サマリー側を直す。

## 形式

1. **四項目構成。** `目的` / `手段` / `結果` / `課題` の順。項目を増やさない、減らさない。
2. **全体で 500 字程度。** 各項目 100〜180 字が目安。四項目の合計で測る。
3. **日本語の地の文。** 箇条書きにしない。見出しは太字（`**目的**`）で置く。
4. **タイトルは付けない。** 著者が Blogger 側で付与する。
5. 記事本文に PR 番号・ブランチ名・コミットハッシュを書かない。読者は差分を見ない。
6. 識別子（`responseBytes`, `mcp.backend.kind` など）は必要な最小限だけ地の文に出す。
   コードブロックは使わない。

## 各項目に書くこと

- **目的** — 改修前に何が問題だったか。「何を良くしたか」ではなく
  「何が間違っていたか」から書く。動機が読者に伝わらない記事は要約として失敗している。
- **手段** — 実際に取った対処。設計判断のうち、外から観測できるものに絞る。
  内部リファクタリングは、観測される振る舞いが変わらないなら書かない。
- **結果** — 検証で確かめられた事実。作業の副産物として見つかった不具合も
  ここに書く。狙って直したものと、途中で気づいたものを区別する必要はない。
- **課題** — 未解決のまま残ったもの。**空にしない。** 残件が本当にないと判断したなら、
  その判断自体を書く。

## 誠実性の規律

この規約の要点は形式ではなくここにある。

- **測っていない効果を書かない。** 「〜が改善した」と書けるのは計測した場合だけ。
  計測していないなら「効果は未測定」と書く。
- **到達不能・未強制・未計測を隠さない。** 実装の弱点は `課題` に名指しで書く。
  外部から先に指摘される種類の欠落こそ、自分で書いておく価値がある。
- **宣伝文句を書かない。** 「大幅に」「劇的に」「完全に」は使わない。
  数字があるなら数字を、ないなら形容詞を落とす。
- 公開範囲によっては弱点の表現を調整してよい。ただし調整するのは表現であって、
  弱点の有無ではない。

## 例（PR #1490 / MCP 契約整合）

> **目的**
>
> AjisaiのMCPサーバーは、実行時間や応答サイズなど10項目の資源上限をエージェントに
> 申告していた。しかしその一部は実際には強制されておらず、応答したバックエンドの
> 識別子も返さず、ホスト側の障害は非構造化の文字列で返していた。申告した契約と
> 実装のずれを塞ぐことが今回の目的である。
>
> **手段**
>
> 応答サイズ上限を両バックエンドで同一単位（UTF-8バイト）で強制し、申告する各上限に
> 境界ケースを一対一で対応させた。上限超過時は、超過した上限名・設定値・実測値を
> 機械可読な形で返す。バックエンドは起動時に固定して応答に明示し、ホスト障害には
> 安定した分類コードと再試行可否を付与、内部詳細はサーバーログに留めた。診断は
> 表示文字列とコードを分離し、未知語には編集距離による候補語を添えた。
>
> **結果**
>
> 両バックエンドが全ゴールデンケースと全上限境界で一致することを確認した。副産物として、
> nativeバックエンドがソースに改行を付加し実効上限を1バイト狭めていた不整合も発見・
> 修正できた。ホストごとの上限差は文書化し、プレイグラウンド側にも適用プロファイルを
> 表示させた。パッケージは公開可能な状態にした。
>
> **課題**
>
> numericWorkなど3項目は、宣言値に到達する前に実行時間上限が先に発火するため実質的に
> 観測できない。内部作業量の見積り再較正が次の課題となる。また診断の改善が実際に
> 修復率を上げるかは未測定であり、実モデルのトレース収集が残っている。
