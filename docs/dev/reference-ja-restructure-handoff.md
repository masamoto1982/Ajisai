## 2. 依頼された 2 点

利用者からの指摘は次の 2 点。

### 2.1 水のメタファーが導入されていない

「NIL と泡（バブル）の規則」で泡という概念に触れているのに、Reference 全体で
水のメタファーにほとんど触れていない。**メタファーは初心者のためにこそある**ので、
「はじめに」のコンセプト説明でまず水のメタファーに触れ、その後もそれになぞらえた
説明が望ましい。

### 2.2 分岐と反復が離れている

分岐（`COND`）と反復について書かれた項目が離れていて、まとまりを欠く。

参考にするサイトとして技術リファレンスの老舗
`https://www.tohoho-web.com/index.htm` が挙げられた。

当該ドメインは本セッションの実行環境では egress プロキシにブロックされたが、
**利用者から Rust 編と Haskell 編の目次が実例として提供された**ので、
そこから読み取れる傾向を §2.3 に記録する。以下はその 2 例からの観察であり、
サイト全体の一般則として確認したものではない。

### 2.3 「とほほ」の目次から読み取れる傾向（実例 2 件より）

**(1) 二階層の目次。大きな主題は親項目にまとめ、小さな主題は最上位に平置きする。**

Haskell 編は最上位 18 項目で、うち 7 つが子項目を持つ
（概要 / 基本 / 型 / 関数 / 制御構文 / データ型…）。
Rust 編も `型`（子 10 個）と `制御構文`（子 6 個）だけが親項目になっている。
**平坦に 30 項目並べるのではなく、6〜8 個の親にまとめている。**

**(2) 見出しに具体的な構文を括弧で併記する。** これが最も特徴的。

> `コメント(//)` / `変数・定数(let, mut, const)` / `条件分岐(if)` /
> `リスト([...])` / `関数合成(.)` / `モジュール (module)` /
> `パッケージ管理(ghc-pkg, cabal)`

概念名だけでも構文だけでもなく**両方**を書く。目次を眺めるだけで
「その言語で何をどう書くか」が分かる。**Ajisai でも採用できる**:
`条件分岐(COND)` / `反復(MAP, FILTER, FOLD)` / `値に名前を付ける(BIND)` /
`ワードの定義(DEF)` / `出力(PRINT)` / `コメント(#)`。

**(3) 制御構文は 1 つの親にまとめる。** 両例とも `制御構文` という親項目を持ち、
その下に分岐・繰り返し・分岐マッチをすべて収めている。
**これは §2.2 の指摘そのものへの答えになっている。**

**(4) 並び順は 概要 → 基本 → 型 → 演算子 → 関数 → 制御構文 → 応用 → リンク。**
Haskell 編がこの型に近い。概要には「〜とは」「言語の特徴」「インストール」
「Hello world」が入る。

**(5) 項目数の目標（利用者指定）: 最上位は多くても 20、理想は 10。**
Ajisai は大規模言語より語ることが少ないので十分に収まる。

> **構造上の注意**: とほほは **1 つの長い HTML ページ＋アンカー目次**である
> （`rust.html#about` のように全項目が同一ページ内アンカー）。一方 Ajisai の
> Reference は **1 セクション＝1 ページ**で、CSS の `:target` で切り替える。
> したがって「二階層の目次」を実現する方法は 2 つある:
> - **(A) セクションを統合して 1 ページを大きくし**、子項目はページ内の `<h3>`
>   アンカーにする。目次は親＝ページリンク、子＝ページ内アンカー。**推奨。**
>   既存の切り替え機構をそのまま使え、ページ数が 20 → 10 前後に減る。
> - (B) 単一スクロールページへ作り替える。`:target` の CSS、スワイプ送り、
>   `aria-current` の同期をすべて書き直すことになる。**非推奨。**

## 3. 調査で判明した重要事項

再編の前に読むこと。いずれも本セッションで一次資料に当たって確認した。

### 3.1 水のメタファーは既にこのプロジェクトの正式な主要メタファーである

これは装飾の追加提案ではない。`README.md` に明記されている（17 行目）:

> The name *Ajisai* comes from hydrangea, often interpreted as a "water vessel."
> **Ajisai uses water as its main metaphor**: values flow through channels,
> operations shape those channels, and exceptional situations remain visible
> instead of disappearing into hidden runtime state.

さらに `README.md` には **"The language in one picture"** という節があり、
そのまま使える対応表が既にある:

| Water metaphor | Language meaning | Observable idea |
| --- | --- | --- |
| Flow | ordinary values moving through the stack | Scalars, booleans, strings, vectors, code blocks |
| Bubble | a well-formed operation could not produce a value | `NIL`, carrying a machine-readable reason |
| Channel error | the operation or input shape is malformed | raised error that propagates and halts evaluation |

**つまり利用者の指摘は「新しい比喩を入れたい」ではなく「宣言済みの設計意図を
Reference が実装していない」という欠陥の指摘である。** 再編ではこの表を
「はじめに」へ持ち込むのが最短かつ最も正当な解になる。

なお、この 3 分類は言語の三分法（値／理由付き不在／エラー）とちょうど対応する。
比喩のために意味論を歪める必要はまったくない。

### 3.2 メタファーは英語版のほうが濃い

現状の出現数:

| 語 | 英語版 | 日本語版 |
| --- | --- | --- |
| bubble / 泡 | 16 | 19（うち大半は `nil` セクションに集中） |
| flow / 流れ | 11 | ほぼ地の文のみ |
| vent | 11 | — |

英語版には `Bubbles flow` / `bubble stays visible` / `bubbled` のような
動詞的な使い方があるが、日本語版は「泡」という名詞の借用にとどまっている。
**日本語版のほうが比喩として痩せている。** ただし英語版も「はじめに」で
メタファーを導入していないので、§2.1 の欠陥は両版に共通する。

### 3.3 「泡」を書いてよい層は Reference だけ

三層モデル（`three-layer-documentation-model.md`）の制約:

- **Layer 1 = Reference** — 比喩・翻訳・richly formatted help が許される層。
  `reference-writing-style.md` §補足も「Bubble Rule の説明では
  『できなかった → 泡 / そもそも使い方が違う → エラー』を採用してよい」と明記。
- **Layer 2 = LOOKUP (`?`)** — UTF-8 English plain text。同文書 §3.3 は
  **「泡」のような日本語散文を使ってはならない**と明記し、`Bubble/NIL` と
  書くよう指示している。
- **正典 `SPECIFICATION.html`** — "bubble" は **0 件**（`grep -ci` で確認）。
  正典は `NIL` としか呼ばない。

**したがって水のメタファーの拡張は Reference 内で完結させること。**
LOOKUP のテキスト（`rust/src/builtins/detail-lookup-*.rs`）や
`SPECIFICATION.html` へ波及させてはならない。この線引き自体が設計判断なので、
比喩を足したついでに正典へ持ち込む、ということをしない。

なお "Bubble Rule" という語は Rust 実装のコメントでは広く使われている
（`rust/src/error.rs` ほか、"SPEC §11.2" として参照）。

### 3.4 【判断済み】正典の向きが逆転する — (a) 一時的な逆転で確定

`public/docs/ja/index.html` の冒頭コメント（11〜20 行目）はこう宣言している:

> このファイルは `public/docs/index.html`（英語版・**正典**）の日本語訳であり…
> 英語版と内容が食い違った場合は英語版が正典（`three-layer-documentation-model.md`
> §2.2: "The English text remains canonical when translations disagree."）。
> **構造・スタイルを変更したときは英語版にも反映すること。**

利用者の計画は「日本語版を大きく再編し、**新しい日本語版から英語版を生成する**」
であり、この宣言と正反対の向きになる。放置すると、ファイル冒頭のコメントが
実際の運用と食い違ったまま残る。

**利用者の判断（2026-08-20、確定）: (a) 一時的な逆転でよい。**

したがって次のように扱う:

- 再編中だけ ja→en の向きで作業し、**英語版再生成の完了をもって英語版を正典へ戻す**。
- `three-layer-documentation-model.md` §2.2 は**変更しない**。
- ja ファイル冒頭コメントの「英語版が正典」という記述も**変更しない**
  （再生成後には再び真になるため）。
- 一時的に逆転している事実は、再編 PR の本文に記録するだけでよい。

**やってはいけないこと**: 「日本語版が正典になった」と読める記述を
ファイル冒頭コメントや方針文書へ書き込むこと。逆転は一時的であり、
恒久的な方針変更ではない。

### 3.5 【既存バグ】ナビの並び順と DOM の並び順が一致していない

Reference は 1 セクション＝1 ページで、CSS の `:target` で表示を切り替える。
ページ送りは 2 経路あり、**この 2 つが違う順序を見ている**:

- サイドバーの目次 — `<nav class="ref-nav">` の `<li>` の並び
- モバイルのスワイプ送り — `goToPageDelta()` が
  `document.querySelectorAll('.ref-page')` すなわち **DOM の並び**を使う
  （`public/docs/ja/index.html` 末尾のスクリプト）

現状 `identity-model`（同一性モデル）は**目次では 5 番目**だが
**DOM では 20 番目（最後）**にある。したがってモバイルで「厳密な数」から
スワイプすると、目次が予告する「同一性モデル」ではなく「スタックと修飾子」へ進む。
`identity-model` はスワイプでは最後尾からしか到達できない。

**英語版もまったく同じ食い違いを持つ**（両版で確認済み）。既存の不整合であって
今回の書き直しで入ったものではない。

**再編では目次だけでなく DOM のセクション順も動かすこと。** 片方だけ直すと
この不整合が残る／増える。

### 3.5b 【確認済み・修正不要】空ベクトル `[ ]` の記述は正しい

「値とベクトル」に「`[ ]` は空ベクトルであり `NIL` ではない」という記述がある。
利用者から「以前の Ajisai では空ベクトルは許されなかったはずで、どこかで仕組みが
変わったのではないか」という確認依頼があった。**調査の結論: 記憶は正しく、
記述も正しい。言語の整合性はむしろ向上している。**

**変更点**: コミット `ed4ea6fe`（2026-08-01）"feat(values): admit the empty Vector"。
それ以前は `[ ]` はエラーだった。コミットメッセージの要旨:

> `LANG.VALUES.VECTOR` は Vector を "an ordered finite collection of values" と
> 定義し、"order and length" を観測可能な構造のすべてとしている。**ゼロは有限の
> 長さである**から、正典は空 Vector を排除していなかった — **排除は実装側の
> 発明だった**。しかもそれには代償があった: `NIL` が「空のコレクション」という
> 二つ目の役割を兼ねる必要があり、これは「理由が不在の観測可能な内容のすべて」と
> する `LANG.VALUES.NIL` と衝突していた。

さらに、`SORT` `UNIQUE` `FILTER` `TAKE` `MAP` `SPLIT` `REMOVE` はいずれも
`projection: {"when":"never"}` と宣言していたのに、空の場合に実際は
`NIL(EmptySequence)` を投影していた — **宣言が偽だった。この変更で真になった。**

**実機で検証済み**（`cargo build --bin ajisai` して `ajisai run` で実行）:

| プログラム | 実測 | 判定 |
| --- | --- | --- |
| `[ ]` | `[ ]` | 値。エラーではない |
| `[ ] LENGTH` | `0/1` | Reference の「`0`」と一致 |
| `[ 1 2 3 ] { 5 GT } FILTER` | `[ ]` | Reference の記述と一致 |
| `[ ] NIL?` | `[ ] FALSE` | 空ベクトルは不在ではない |
| `[ ] SORT` / `UNIQUE` / `ORDER` / `REVERSE` / `TALLY` / `MAP` | `[ ]` | NIL を出さない |
| `[ ] SUM` | `0/1` | 加法の単位元。妥当 |
| `[ ] JOIN` | `''` | 連結の単位元。妥当 |
| `[ ] [ 0 ] GET` | `NIL` | 範囲外なので泡。正しい |

**したがって Reference は修正不要。** 空ベクトルは各ワードで単位元として
一貫して振る舞っており、整合性の問題は見つからなかった。

**ただし 1 箇所、実装側にコメントの陳腐化がある**（コードコメントであり
reading surface ではないので緊急ではない）:
`rust/src/interpreter/nil_conformance_tests.rs` に
「`emptyVector`, a condition no program can reach because **an empty vector is
inexpressible**」という記述が残っている。空ベクトルは現在 expressible なので
**理由が古い**。ただし結論（`SORT`/`UNIQUE` は `never` でよい）は上表のとおり
別の理由で今も正しいので、バグではない。`ed4ea6fe` のコミットメッセージ自身が
「古い法則は自らの終わりを予言していた」と書いており、この文はその取り残しである。

### 3.6 制御構造が 3 箇所に分散し、フレーム表が重複している

「分岐と反復」の実体は現状 3 セクションに散っている:

| 位置 | セクション | 制御構造としての役割 |
| --- | --- | --- |
| 12 | 高階ワード | `MAP` `FILTER` `FOLD` `ANY` `ALL` — **反復の実体** |
| 13 | 条件分岐 | `COND` — 分岐。`COND` による再帰にも触れる |
| 18 | 反復計算と数値 | 反復の**コスト**と `QUANTIZE`、閉じた形 |

12 と 13 は隣接しているが、18 との間に「文字列」「ワードの定義」
「値に名前を付ける」「よくあるパターン」の 4 セクションが挟まっている。

さらに**同じ概念が 2 セクションに分かれている**:

- 高階ワード §「ブロックが見るもの」— ブロックの評価文脈を **5 行の表**で説明
- 条件分岐 §「節が見るもの」— `COND` 節の評価文脈を説明し、
  「5 つの規則をまとめて見るには[ブロックが見るもの]を参照」と**逆参照している**

つまりフレーム（評価文脈）の概念は高階ワード側に住んでいて、`COND` がそれを
借りに行く形になっている。制御構造をまとめるなら、ここを 1 つにできる。

## 4. 水のメタファー適用方針

### 4.1 適用する

1. **「はじめに」に導入を置く。** §3.1 の README 表を日本語化して載せ、
   三分法（値／泡／エラー）と対応づける。ここが利用者の要望の中心。
2. **`NIL` セクション**は既に泡で書かれている。導入と接続し、用語を揃える。
3. **論理セクション**の NIL passthrough は「泡が下流へ流れる」で説明できる。
   既に「泡は流れる」という見出しがある。
4. **`VENT` (`^`)** は比喩上きれいに嵌まる（泡を逃がす弁）。既存記述を強化する。
5. **dataflow = データの流れ**。「はじめに」の 1 文目で既に使える。

### 4.2 適用しない（守ること）

- **LOOKUP と正典へ波及させない。** §3.3 の線引きを越えない。
- **比喩で厳密さを置き換えない。** 「〜のようなもの」で済ませて実際の規則を
  書かない、は不可。比喩は規則の**導入**であって規則の**代用**ではない。
  既存セクションはこの点で質が高いので、水位を下げないこと。
- **検証済みのサンプルコードと期待値を変えない。** 変える必要が生じたら、
  それは構成の問題ではなく事実の問題なので、実装に当たって確認すること。
- **比喩語を無制限に増やさない。** 「流れ／泡／水路」で足りるはず。
  「沈む」「濁る」「蒸発する」のような語を足すと、対応する意味論が無いのに
  意味ありげに読めてしまう。

### 4.3 用語対訳の更新が要る

`public/docs/ja/index.html` の冒頭コメント 30〜31 行目に用語対訳表がある:

```
用語対訳: word=ワード, stack=スタック, vector=ベクトル, bubble=泡
（バブル）, block=ブロック, frame=フレーム, bind=束縛, dictionary=辞書。
```

`flow` と `channel error` の訳語が無い。**再編で新語を導入するならここに追記する。**
特に `channel error` は要検討（「水路のエラー」「チャネルエラー」「水路の破れ」など）。
現状の日本語版は単に「エラー」と書いており、比喩名を持っていない。
**訳語は利用者に確認してから確定すること。**

| 4 | `stack` | スタックと修飾子(`KEEP`) | スタックの基本／`KEEP`／高階ワードだけの例外 | 6 |
| 5 | `operators` | 演算子(`+ - * / %`, `=`, `AND`) | 算術／ブロードキャスト／比較／論理 | 7+8+9 を統合 |
| 6 | `vector-ops` | ベクトル操作(`GET`, `LENGTH`) | `GET`／答えの形／その他／順序付け・計数・形状 | 11 |
| 7 | `strings-ops` | 文字列操作(`CHARS`, `JOIN`) | `CHARS`／`JOIN`／`TRIM`／`TOKENIZE`／`STR`・`NUM` | 14 の操作部分 |
| 8 | `control` | **制御構文**(`COND`, `MAP`) | ブロックと評価文脈(`{ }`)／条件分岐(`COND`)／反復(`MAP` `FILTER` `FOLD` `ANY` `ALL`)／反復のコスト(`QUANTIZE`) | **12+13+18 を統合** |
| 9 | `words` | ワードと名前(`DEF`, `BIND`) | ワードの定義(`DEF`)／値に名前を付ける(`BIND`)／辞書とワードの同一性 | 15+16+19 を統合 |
| 10 | `output` | 出力(`PRINT`) | `PRINT`／引用符は表示上の便宜 | 20 |
| 11 | `patterns` | よくあるパターン | 積・内積・argmin・分散／キーによる順序付け／付録: 同一性モデル | 17＋**5 を吸収** |

**最上位 11 項目。** 利用者指定の「多くても 20、理想は 10」に収まる。

### 5.2 各変更の理由

- **#8 `control` への統合が §2.2 の指摘への直接の答え**。分岐・反復・反復コストが
  1 ページに揃い、`制御構文` という親項目になる（§2.3 の傾向 (3) と一致）。
  同時に §3.6 のフレーム表の重複も解消する — 「ブロックと評価文脈」を
  ページ先頭の子項目にすれば、`COND` も高階ワードも同じページ内で参照できる。
- **#3 `values` への統合**: 値の定義域（ベクトル・数・文字列・真偽値・泡）を 1 ページに
  集める。**水のメタファーの三分法（流れ／泡／水路のエラー）がここで完結する**ので、
  §4 の比喩導入と噛み合う。
- **#5 `operators` への統合**: 算術・比較・論理はいずれも「二項＋リフト」で
  構造が同じ。とほほも `演算子` を 1 項目にしている。
- **#7 `strings-ops` を分離**: 文字列の**型**は #3 へ、**操作**は #7 へ分ける。
  ベクトル操作(#6)と対になり、`CHARS` でベクトル領域へ渡るという関係が見えやすい。
- **#11 が `identity-model` を吸収**: 4 層の等価性は付録的な話題。
  現状は目次 5 番目という不相応な位置にある。
- **見出しへの構文併記**（§2.3 傾向 (2)）は全項目で採用する。

### 5.3 統合しない選択肢（リスク低）

ページ統合は差分が大きい。**最小で §2.2 に応えるだけなら**、平坦な 20 ページを
保ったまま `iterative` を `higher-order`/`cond` の隣へ移すだけでもよい。
ただしこの場合 §2.3 の「二階層・10 項目」という目標には届かない。
**どちらを採るか利用者に確認すること。**

### 5.4 統合作業で失ってはいけないもの

ページ統合は「切り貼り」ではない。統合後も次を保つこと:

- **既存の `<h3 id="...">` は id を変えない**（`#ordering` `#blocks-frames`
  `#two-arguments` `#name-inside-brackets`）。ページが変わってもアンカーは生きる。
- **旧ページ id への外部リンクが切れる**。`#numbers` `#logic` `#cond` などは
  公開 URL としてすでに存在しうる。統合で消える id については、
  **少なくとも PR 本文に「どの id がどこへ吸収されたか」の対応表を残すこと。**
  必要なら統合先ページに `<h3 id="numbers">` のような形で id を温存できる。
- **検証済みサンプルと期待値は 1 つも落とさない。** 統合の過程で例が消えるのが
  いちばん起きやすい事故。統合の前後で総数を数えて比較すること:

  ```
  grep -o '<div class="sample">' public/docs/ja/index.html | wc -l   # 現在 79
  grep -o 'js-open-playground'   public/docs/ja/index.html | wc -l   # 現在 79
  ```

  この 2 つは一致していなければならない（サンプル 1 つにつき Playground ボタン 1 つ）。
  なお `grep -c 'class="sample"'` は `sample-actions` にも当たるので使わないこと。

## 6. 作業手順

### 6.1 分割方針

**1 PR で全部やらないこと。** 直前の書き直しは 1 セクション 1 PR で進めて
うまくいった。再編も同じ粒度が望ましいが、順序変更は本質的に横断的なので、
次の 3 段階を推奨する:

1. **メタファー導入 PR** — 「はじめに」への導入 ＋ 用語対訳表の更新。
   順序は変えない。ここだけで利用者は §2.1 の成否を判断できる。
2. **順序変更 PR** — DOM のセクション順と目次の並びを**同時に**変更。
   §3.5 の不整合もここで解消する。本文には触れない。
3. **統合 PR**（§5.3 で新設を採る場合のみ）— `blocks` セクションの切り出しと、
   `COND` 側の逆参照の整理。

### 6.2 順序変更で壊れやすいもの

- **セクション内アンカー**: `#ordering` / `#blocks-frames` / `#two-arguments` /
  `#name-inside-brackets` は本文中から相互参照されている。移動しても
  **id は変えないこと**。変えるなら参照元をすべて追うこと。
- **相互参照リンク**: `href="#..."` は本文中に多数ある。
  `grep -o 'href="#[a-z-]*"' public/docs/ja/index.html | sort -u` で洗い出し、
  移動後にすべて解決することを確認する。
- **「前節で述べた」式の前後依存**: 順序を変えると嘘になる。
  移動したセクションの前後 1 段落は必ず読み直すこと。

### 6.3 英語版の扱い

**再編中は英語版に触れない。** 日本語版が固まってから、別セッションで
英語版を再生成する（§3.4 の確認結果に従う）。その際:

- 英語版にも §3.5 の nav/DOM 不整合がある。同じ順序へ揃えること。
- 英語版の水のメタファーは日本語版より濃い（§3.2）。単純な翻訳ではなく、
  既にある `Bubbles flow` などの表現を活かすこと。
- `public/docs/index.html` の冒頭にも同種の運用コメントがあるか確認すること。
