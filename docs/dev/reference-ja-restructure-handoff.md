## 3. 調査で判明した重要事項

再編の前に読むこと。いずれも本セッションで一次資料に当たって確認した。

### 3.1 水のメタファーは既にこのプロジェクトの正式な主要メタファーである

これは装飾の追加提案ではない。`README.md` に明記されている（17 行目）:

> The name *Ajisai* comes from hydrangea, often interpreted as a "water vessel."
> **Ajisai uses water as its main metaphor**: values flow through channels,
> operations shape those channels, and exceptional situations remain visible
> instead of disappearing into hidden runtime state.

さらに `README.md` には **"The language in one picture"** という節があり、
そのまま使える対応表が既にある:

| Water metaphor | Language meaning | Observable idea |
| --- | --- | --- |
| Flow | ordinary values moving through the stack | Scalars, booleans, strings, vectors, code blocks |
| Bubble | a well-formed operation could not produce a value | `NIL`, carrying a machine-readable reason |
| Channel error | the operation or input shape is malformed | raised error that propagates and halts evaluation |

**つまり利用者の指摘は「新しい比喩を入れたい」ではなく「宣言済みの設計意図を
Reference が実装していない」という欠陥の指摘である。** 再編ではこの表を
「はじめに」へ持ち込むのが最短かつ最も正当な解になる。

なお、この 3 分類は言語の三分法（値／理由付き不在／エラー）とちょうど対応する。
比喩のために意味論を歪める必要はまったくない。

### 3.2 メタファーは英語版のほうが濃い

現状の出現数:

| 語 | 英語版 | 日本語版 |
| --- | --- | --- |
| bubble / 泡 | 16 | 19（うち大半は `nil` セクションに集中） |
| flow / 流れ | 11 | ほぼ地の文のみ |
| vent | 11 | — |

英語版には `Bubbles flow` / `bubble stays visible` / `bubbled` のような
動詞的な使い方があるが、日本語版は「泡」という名詞の借用にとどまっている。
**日本語版のほうが比喩として痩せている。** ただし英語版も「はじめに」で
メタファーを導入していないので、§2.1 の欠陥は両版に共通する。

### 3.3 「泡」を書いてよい層は Reference だけ

三層モデル（`three-layer-documentation-model.md`）の制約:

- **Layer 1 = Reference** — 比喩・翻訳・richly formatted help が許される層。
  `reference-writing-style.md` §補足も「Bubble Rule の説明では
  『できなかった → 泡 / そもそも使い方が違う → エラー』を採用してよい」と明記。
- **Layer 2 = LOOKUP (`?`)** — UTF-8 English plain text。同文書 §3.3 は
  **「泡」のような日本語散文を使ってはならない**と明記し、`Bubble/NIL` と
  書くよう指示している。
- **正典 `SPECIFICATION.html`** — "bubble" は **0 件**（`grep -ci` で確認）。
  正典は `NIL` としか呼ばない。

**したがって水のメタファーの拡張は Reference 内で完結させること。**
LOOKUP のテキスト（`rust/src/builtins/detail-lookup-*.rs`）や
`SPECIFICATION.html` へ波及させてはならない。この線引き自体が設計判断なので、
比喩を足したついでに正典へ持ち込む、ということをしない。

なお "Bubble Rule" という語は Rust 実装のコメントでは広く使われている
（`rust/src/error.rs` ほか、"SPEC §11.2" として参照）。

### 3.4 【要判断】正典の向きが逆転する

`public/docs/ja/index.html` の冒頭コメント（11〜20 行目）はこう宣言している:

> このファイルは `public/docs/index.html`（英語版・**正典**）の日本語訳であり…
> 英語版と内容が食い違った場合は英語版が正典（`three-layer-documentation-model.md`
> §2.2: "The English text remains canonical when translations disagree."）。
> **構造・スタイルを変更したときは英語版にも反映すること。**

利用者の計画は「日本語版を大きく再編し、**新しい日本語版から英語版を生成する**」
であり、この宣言と正反対の向きになる。放置すると、ファイル冒頭のコメントが
実際の運用と食い違ったまま残る。

**次セッションは、着手前に利用者へ次のいずれかを確認すること:**

- (a) 今回だけ例外的に ja→en とし、英語版再生成の完了をもって英語版を正典へ戻す。
  → ja ファイルの冒頭コメントは**再生成完了後に**現状のまま維持できる。
     再編中の一時的な逆転は PR 本文に記録するだけでよい。
- (b) 恒久的に日本語版を正典とする。
  → `three-layer-documentation-model.md` §2.2 と ja/en 両ファイルの冒頭コメントを
     更新する必要がある。**正典方針の変更なので利用者の明示的な承認が要る。**

推奨は (a)。方針文書の変更は再編とは別の判断であり、混ぜると差分が読みにくい。

### 3.5 【既存バグ】ナビの並び順と DOM の並び順が一致していない

Reference は 1 セクション＝1 ページで、CSS の `:target` で表示を切り替える。
ページ送りは 2 経路あり、**この 2 つが違う順序を見ている**:

- サイドバーの目次 — `<nav class="ref-nav">` の `<li>` の並び
- モバイルのスワイプ送り — `goToPageDelta()` が
  `document.querySelectorAll('.ref-page')` すなわち **DOM の並び**を使う
  （`public/docs/ja/index.html` 末尾のスクリプト）

現状 `identity-model`（同一性モデル）は**目次では 5 番目**だが
**DOM では 20 番目（最後）**にある。したがってモバイルで「厳密な数」から
スワイプすると、目次が予告する「同一性モデル」ではなく「スタックと修飾子」へ進む。
`identity-model` はスワイプでは最後尾からしか到達できない。

**英語版もまったく同じ食い違いを持つ**（両版で確認済み）。既存の不整合であって
今回の書き直しで入ったものではない。

**再編では目次だけでなく DOM のセクション順も動かすこと。** 片方だけ直すと
この不整合が残る／増える。

### 3.6 制御構造が 3 箇所に分散し、フレーム表が重複している

「分岐と反復」の実体は現状 3 セクションに散っている:

| 位置 | セクション | 制御構造としての役割 |
| --- | --- | --- |
| 12 | 高階ワード | `MAP` `FILTER` `FOLD` `ANY` `ALL` — **反復の実体** |
| 13 | 条件分岐 | `COND` — 分岐。`COND` による再帰にも触れる |
| 18 | 反復計算と数値 | 反復の**コスト**と `QUANTIZE`、閉じた形 |

12 と 13 は隣接しているが、18 との間に「文字列」「ワードの定義」
「値に名前を付ける」「よくあるパターン」の 4 セクションが挟まっている。

さらに**同じ概念が 2 セクションに分かれている**:

- 高階ワード §「ブロックが見るもの」— ブロックの評価文脈を **5 行の表**で説明
- 条件分岐 §「節が見るもの」— `COND` 節の評価文脈を説明し、
  「5 つの規則をまとめて見るには[ブロックが見るもの]を参照」と**逆参照している**

つまりフレーム（評価文脈）の概念は高階ワード側に住んでいて、`COND` がそれを
借りに行く形になっている。制御構造をまとめるなら、ここを 1 つにできる。

## 4. 水のメタファー適用方針

### 4.1 適用する

1. **「はじめに」に導入を置く。** §3.1 の README 表を日本語化して載せ、
   三分法（値／泡／エラー）と対応づける。ここが利用者の要望の中心。
2. **`NIL` セクション**は既に泡で書かれている。導入と接続し、用語を揃える。
3. **論理セクション**の NIL passthrough は「泡が下流へ流れる」で説明できる。
   既に「泡は流れる」という見出しがある。
4. **`VENT` (`^`)** は比喩上きれいに嵌まる（泡を逃がす弁）。既存記述を強化する。
5. **dataflow = データの流れ**。「はじめに」の 1 文目で既に使える。

### 4.2 適用しない（守ること）

- **LOOKUP と正典へ波及させない。** §3.3 の線引きを越えない。
- **比喩で厳密さを置き換えない。** 「〜のようなもの」で済ませて実際の規則を
  書かない、は不可。比喩は規則の**導入**であって規則の**代用**ではない。
  既存セクションはこの点で質が高いので、水位を下げないこと。
- **検証済みのサンプルコードと期待値を変えない。** 変える必要が生じたら、
  それは構成の問題ではなく事実の問題なので、実装に当たって確認すること。
- **比喩語を無制限に増やさない。** 「流れ／泡／水路」で足りるはず。
  「沈む」「濁る」「蒸発する」のような語を足すと、対応する意味論が無いのに
  意味ありげに読めてしまう。

### 4.3 用語対訳の更新が要る

`public/docs/ja/index.html` の冒頭コメント 30〜31 行目に用語対訳表がある:

```
用語対訳: word=ワード, stack=スタック, vector=ベクトル, bubble=泡
（バブル）, block=ブロック, frame=フレーム, bind=束縛, dictionary=辞書。
```

`flow` と `channel error` の訳語が無い。**再編で新語を導入するならここに追記する。**
特に `channel error` は要検討（「水路のエラー」「チャネルエラー」「水路の破れ」など）。
現状の日本語版は単に「エラー」と書いており、比喩名を持っていない。
**訳語は利用者に確認してから確定すること。**

### 5.2 各変更の理由

- **`strings` を 14→5**: 文字列は 6 つの値の定義域の 1 つ。値の部にあるべきで、
  現状は分岐と抽象化の間に挟まって流れを切っている。
- **`iterative` を 18→15**: §2.2 の指摘への直接の対応。反復の実体（高階ワード）と
  そのコスト（反復計算と数値）を隣接させる。
- **`blocks` 新設**: §3.6 の重複解消。高階ワードの「ブロックが見るもの」の 5 行表を
  制御構造の部の先頭へ独立させ、`COND` と高階ワードの両方がそこを参照する形にする。
  結果として「節が見るもの」の逆参照が自然になる。
- **`identity-model` を 5→21**: 4 層の等価性という抽象度の高い話が、読者がまだ
  スタックにも触れていない 5 番目に置かれている。付録が妥当。
  **加えて §3.5 のバグが自動的に解消する**（DOM でも既に最後尾なので、
  目次を DOM に合わせれば両者が一致する）。
- **`nil` は動かさない**: 泡の**語彙**は「はじめに」で導入するが、泡を
  **扱う**説明（`NIL?` / `NIL-REASON` / `VENT`）は `/` や `GET` や `NUM` を
  使う例に依存する。演算の後に置くのが正しい。

### 5.3 より小さい代案

`blocks` の新設はページ数が増える。**リスクを抑えるなら**「ブロックが見るもの」を
高階ワード内に残したまま、順序変更（`strings` / `iterative` / `identity-model`）だけ
行う案もある。§2.2 の指摘には順序変更だけでも応えられる。
どちらを採るか利用者に確認すること。

## 6. 作業手順

### 6.1 分割方針

**1 PR で全部やらないこと。** 直前の書き直しは 1 セクション 1 PR で進めて
うまくいった。再編も同じ粒度が望ましいが、順序変更は本質的に横断的なので、
次の 3 段階を推奨する:

1. **メタファー導入 PR** — 「はじめに」への導入 ＋ 用語対訳表の更新。
   順序は変えない。ここだけで利用者は §2.1 の成否を判断できる。
2. **順序変更 PR** — DOM のセクション順と目次の並びを**同時に**変更。
   §3.5 の不整合もここで解消する。本文には触れない。
3. **統合 PR**（§5.3 で新設を採る場合のみ）— `blocks` セクションの切り出しと、
   `COND` 側の逆参照の整理。

### 6.2 順序変更で壊れやすいもの

- **セクション内アンカー**: `#ordering` / `#blocks-frames` / `#two-arguments` /
  `#name-inside-brackets` は本文中から相互参照されている。移動しても
  **id は変えないこと**。変えるなら参照元をすべて追うこと。
- **相互参照リンク**: `href="#..."` は本文中に多数ある。
  `grep -o 'href="#[a-z-]*"' public/docs/ja/index.html | sort -u` で洗い出し、
  移動後にすべて解決することを確認する。
- **「前節で述べた」式の前後依存**: 順序を変えると嘘になる。
  移動したセクションの前後 1 段落は必ず読み直すこと。

### 6.3 英語版の扱い

**再編中は英語版に触れない。** 日本語版が固まってから、別セッションで
英語版を再生成する（§3.4 の確認結果に従う）。その際:

- 英語版にも §3.5 の nav/DOM 不整合がある。同じ順序へ揃えること。
- 英語版の水のメタファーは日本語版より濃い（§3.2）。単純な翻訳ではなく、
  既にある `Bubbles flow` などの表現を活かすこと。
- `public/docs/index.html` の冒頭にも同種の運用コメントがあるか確認すること。
