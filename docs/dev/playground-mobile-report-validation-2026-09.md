# Playground モバイルモード改善提案書（外部）の妥当性確認と改修（2026-09）

Status: 非正典・`[方針記録]`。本書は Ajisai の意味論も互換性方針も定義しない。
正典は `spec/` 配下の各ソースと、そこから生成される `SPECIFICATION.html` のみ。

## 0. 出所

外部セッションが Playground（https://masamoto1982.github.io/Ajisai/）を
実効ビューポート幅 約300px CSS のモバイル縦で検証し、画面表示・DOM/CSS 実測・
イベント発火から 12 件（高5・中4・低3）を挙げた改善提案書。本書はその
**妥当性を実装に当たって独立に確認した結果**と、そこから実施した改修の記録である。

先行する `playground-report-validation-2026-09.md` は言語処理・診断・Reference
同期の検証であり、こちらは操作面（モバイル）の検証である。所見番号は提案書の
ものをそのまま引く（H-1〜H-5 / M-1〜M-4 / L-1〜L-3）。**提案書が挙げなかった
所見**は §2 に A〜E として別立てで記録する。

## 1. 判定

| --- | --- | --- |

## 2. 提案書が挙げなかった所見

提案書は「画面に見えるもの」を丁寧に測っているが、**イベントの側**は
「イベント発火で再現できなかった」として要確認事項に送っている。実装を読むと、
そこに提案書の高severity項目と同格かそれ以上の問題があった。

- **A. Reset / Step / Abort / Lookup にモバイルの導線が一切無い。** 4 つとも
  `window` の `keydown` にしか結線されていない。ハードウェアキーボードを持たない
  端末では、プログラムを1ステップずつ走らせることも、辞書を引くことも、
  全消去することもできなかった。H-1（Run ボタンが無い）は、この穴の**一部**に
  過ぎない。
- **B. パネル切替スワイプが `document.body` に結線されており、開始要素を見ていない。**
  エディタ内で横方向にドラッグして範囲選択すると、`deltaX > 50px` でそのまま
  パネルが切り替わり、書いていたコードの画面から出てしまう。辞書検索欄でも同じ。
- **C. トリプルタップ判定が `touchend` を無条件に数えていた。** 移動量も
  同時タッチ数も見ていないので、ドラッグ選択の終端も、ピンチの各指のリリースも
  1タップとして数えられた。3つ貯まればプログラムが走る。提案書の H-2 が
  「ダブルタップ拡大と競合する恐れ」と書いた懸念は、拡大より先に**意図しない実行**
  として出る。
- **D. プレースホルダのチートシートがスワイプを書いていない。** 4 面すべてを
  巡回できる唯一の指ジェスチャーが未記載で、2 面ぶんのダブルタップだけが
  書かれていた。
- **E. 辞書検索欄も 16px 未満。** H-3 と同じ iOS 自動ズームが起きる。
- **F. モバイルのセレクタ行自体が横にはみ出していた。** 300px 幅で計測すると
  `.area-selector-mobile` は `scrollWidth 313 / clientWidth 300`。`.vocabulary-search-input`
  の `min-width: 120px` がこの行の取り分より広く、検索欄とその `×` が右端から
  12.5px はみ出す。提案書が「横スクロールが発生しない」と結論したのは
  `document.documentElement` で測ったためで、そちらは body が切り落とすので
  一致する——**はみ出しは文書ではなく行の中にあった**。測る対象を 1 階層
  下げないと見えない種類の崩れである。

## 3. 実施した改修

### 3.1 タッチアクションバー（H-1 / A / L-2）

`index.html` の Input 面に `#editor-touch-actions` を追加し、Run / Step / Stop /
Look up / Reset を並べた。モバイル表示でのみ現れる（デスクトップは同じ操作を
プレースホルダがショートカットとして書いている）。

- Reset はショートカットと同じ `RESET_CONFIRM_MESSAGE` で確認する。確認文字列を
  2 箇所に書き分けないよう定数にした。
- Stop は Escape 分岐と同じ `WORKER_MANAGER.abortAll()` + `abortExecution()` の
  対で、実行中でなくても無害である。
- Lookup はカーソル位置の語を引くが、ボタンを押すとテキストエリアからフォーカスが
  外れる。`getWordAtCursor` を `element.selectionStart` の直読みから
  `lookupEditableSelectionRange()`（blur 時に同期される最後のキャレット）に
  変えた。この関数は同じ理由で既に存在していたが、`getWordAtCursor` だけが
  使っていなかった。
- トリプルタップは残した。**上級者向けショートカットとして併存させる**という
  提案書の案どおりで、これは唯一の導線であることをやめただけである。

### 3.2 タップ・スワイプ判定の作り直し（H-2 / B / C）

`src/gui/touch-gestures.ts` を新設し、判定の純粋な核を 1 箇所に集めた。

- `createMultiTapRecognizer` は、間隔（時間）と**run の先頭タップからの移動量**の
  両方が範囲内である間だけ同じ run として数える。前のタップからの相対で測ると、
  許容量ずつ画面を横断していく「間の空いたドラッグ」が多重タップとして通って
  しまうため、アンカーは先頭で固定している。
- `checkIsStationary` が、押した場所と離した場所が同じかを見る。エディタの
  `touchstart`/`touchend` を対にして、ドラッグ選択の終端をタップから外した。
  同時タッチが 2 本になった時点、および離した時点で指が残っている場合は run を
  破棄する（ピンチ対策）。
- `detectSwipeDirection` は `mobile-view-switcher.ts` から移し、`checkIsSwipeExempt`
  を足した。`textarea` / `input` / `select` / `.editor-suggestions` 上で始まった
  横ドラッグは、その要素自身の選択・スクロールであってレイアウトへの指示ではない。
- エディタ・Stack 面・Output 面・各ボタンに `touch-action: manipulation` を
  付けた。ダブルタップ拡大だけを手放し、ピンチ拡大とスクロールは残す。提案書が
  勧めた `user-scalable=no` は採らない——拡大を禁じるのはアクセシビリティの
  後退であり、必要なのは「タップ数を数える要素で拡大ショートカットを黙らせる」
  ことだけである。
- 新設分は `src/gui/touch-gestures.test.ts`（17 ケース）で固定した。閾値の境界、
  run のドリフト、垂直ドラッグ（＝スクロール）の除外を含む。

### 3.3 文字サイズとタップ領域（H-3 / H-5 / L-3 / E）

`components.css` のモバイルブロックに 2 本の規則を通した。

- キャレットを持つものは 1rem 以上（`#code-input`, `.vocabulary-search-input`,
  `.area-selector select`）。16px 未満で iOS Safari がフォーカス時にズームし、
  自動では戻らない。
- 押すためのものは短辺 2.75rem（44px）以上。`.inline-clear-btn` は**描かれる
  グリフの大きさを変えずに**当たり判定だけを広げ（透明な余白）、角に寄せ直した。
  LaTeX トグル・辞書の単語ボタン・ヘッダの `.btn` も同じ床に揃えた。

300px 幅・DPR2 の実機相当（Chromium, `isMobile: true, hasTouch: true`）で
前後を実測した。改修前の値は提案書の実測表と一致している。

| 要素 | 改修前 | 改修後 |
| --- | --- | --- |
| `#code-input` のフォント | 15.2px | 16px |
| `.vocabulary-search-input` のフォント | 13.6px | 16px |
| `#mobile-panel-select` | 高さ 27px / 12.8px | 高さ 44px / 16px |
| `#editor-clear-btn`・`#editor-format-btn`・`#stack-clear-btn` | 24 × 24px | 44 × 44px |
| `.stack-latex-toggle`（label 全体） | 高さ 約19px（checkbox 13px） | 高さ 44px（checkbox 20px） |
| `.word-button`（辞書の単語） | 45.7 × 31px | 45.7 × 44px |
| `.dictionary-sheet-select` | 高さ 27px | 高さ 44px |
| `.area-selector-mobile` の内容幅 | 313px（300px に対し13px 超過） | 300px |
| ヘッダの `.btn` | 高さ 34px | 高さ 44px |

記号パレットのセルだけは 2.25rem（36px）のまま据え置いた。提案書自身が
「良かった点」として押しやすさを認めており、6列×5行を 44px にすると
その下にあるエディタから 40px を余計に奪うため。

`.vocabulary-search-input` の `min-width` を 0 に落として F を潰し、辞書シート
セレクタ（`.dictionary-sheet-select`）も同じ 44px の床に載せた。後者は
`.area-selector` の外にあるため、セレクタと同じ基底規則で並んでいながら
今回の床から漏れていた。

### 3.4 記号パレットを非重畳に（H-4）

モバイルでは `.editor-suggestions--symbols` を `position: static` にしてフローに
戻し、`order` で Input 面の下端（アクションバーの上）に置いた。テキストエリアは
`flex: 1` なので自分で縮む。キャレット追従の絶対配置は**単語補完の側だけ**に
残した——そちらは打っているテキストに属する表示である。

### 3.5 辞書の使用例を折り返す（M-2）

`.dictionary-sheet .word-info-display` の `nowrap` + 固定高を外し、最大3行で
折り返すようにした（`-webkit-line-clamp`）。1行ぶんの最低高は残してあるので、
選択が「例のある語」と「無い語」の間を動いても一覧が跳ねない。

### 3.6 補完の発火条件とチートシート（M-3 / D）

- `MIN_SUGGESTION_TRIGGER_LENGTH` を 3 から 2 に下げた。上限は `MAX_SUGGESTIONS`
  の 10 件のままなので、短い接頭辞の代償は「候補が長くなる」であって
  「無制限になる」ではない。
- モバイルのプレースホルダを書き直した。ボタンを先に、ジェスチャーを後に並べ、
  スワイプを明記した。画面にあるものは見つかるが、ジェスチャーは教えられなければ
  存在しないため。デスクトップ版より**短く**してある——記号パレットが下に開いて
  エディタが場所を譲る（§3.4）ので、残す行は残す価値のある行でなければならない。
  4面すべてを巡回できるスワイプが載り、2遷移ぶんのダブルタップは落とした。

### 3.7 正典と設計メモの同期

- `spec/gui-semantics.md` の「Current GUI contract」に、モバイル表示が持つ
  控えの列を書き加えた。規範規則を 3 本から 4 本に増やし、4 本目を
  **「No operation is keyboard-only」**とした。ショートカットは最速の経路で
  あってよいが唯一の経路であってはならず、ジェスチャーも唯一の経路であっては
  ならない（画面はジェスチャーの存在を示さないため）、という規則である。
  H-1 と §2 A は、この規則が無かったために誰にも落とし穴と認識されていなかった。
  `SPECIFICATION.html` は `npm run specification:generate` で再生成済み。
- `docs/dev/gui-current-design-memory.md` の「Run via button」「Test button」は
  どちらも実在しない控えを現在形で述べていた。実態に直し、経緯も残した。
  モバイルのタッチ操作の節を新設した。

## 4. 未着手（妥当と確認したが今回やらないもの）

| 項目 | 理由 |
| --- | --- |
| M-1 / M-4 のタブ UI 化・遷移アニメーション | ドロップダウンは 44px に揃えた。4 面のセグメント化は 300px 幅でのラベル設計を含む別作業で、今回のスワイプ修正で切替コスト自体は下がっている |
| M-1 の「Input→Stack→Output の縦連結表示」 | Presentation Profile の「one selected surface at a time」を変える提案であり、正典の判断が要る。tuning ではない |
| 記号パレット表示中はチートシートが読み切れない | パレットが開くのは空エディタにフォーカスした瞬間で、そのときエディタは 160px 程度になる。プレースホルダを短くし重要な行を先頭に寄せたが、全文を読むにはテキストエリアをスクロールするか入力を始める必要がある。提案書が勧めた「折りたたみ可能な常設ヘルプバー」は UI の新設であり、別途判断 |
| ソフトキーボード表示中のアクションバーの位置 | `visualViewport` に追随させる案がある。今回はバーを Input 面の内側に置くところまで。iOS ではレイアウトビューポートが縮まないため、キーボードがバーを覆う場合がある |
| 提案書の「要確認事項」3 件の実機再確認 | ダブルタップ遷移・ペースト/IME 入力は実機でしか確定しない。ただしダブルタップ遷移については判定側を作り直したので、再確認は改修後の版に対して行う必要がある |

## 5. 撤回（2026-09-21）——実機で使った所有者の報告により

§3.1 のタッチアクションバーと §3.4 の記号パレット非重畳化、そして §3.2 の
スワイプ除外リストを**撤回した**。所有者が実際にスマートフォンで使ったところ、
改修前より明確に使いにくくなっていたためである。

### 5.1 何が起きていたか（360×740 で実測）

| | 撤回前 | 撤回後 |
| --- | --- | --- |
| エディタ高さ（未フォーカス） | 383.6px | 496.8px |
| エディタ高さ（フォーカス時） | **179.6px** | **496.8px** |
| エディタ上でのスワイプ | 効かない | 効く |

フォーカスするとエディタが 179.6px まで潰れる。アクションバー 96px と
フロー配置の記号パレット 196px が、エディタ本体より広い面積を取っていた。
**プレイグラウンドの主役はエディタである。** その主役を 3 分の 1 にしてまで
置く価値のある控えではなかった。

スワイプは `checkIsSwipeExempt` が殺していた。`textarea` 上で始まった横ドラッグ
は「範囲選択だから」レイアウトに渡さない、という判断だったが——**タッチ画面では
横ドラッグはテキストを選択しない。** 選択は長押し＋選択ハンドルという別の操作系
である。除外リストは起きない問題に備えて、Input 面のほぼ全域でスワイプを無効化
していた。所有者の「フッターでスワイプすると切り替わることがある」という報告が
まさにこれで、フッターだけが除外リストの外だった。

### 5.2 判断の誤り方

§2 A（Reset / Step / Abort / Lookup がモバイルから到達不能）は事実としては
正しい。誤ったのは**その埋め方の値段を測らなかったこと**である。到達可能性は
画面積と交換になる。交換レートを測らずに「規範規則」まで立ててしまうと、
規則が自分で自分を正当化しはじめる。

もうひとつ。Ajisai を**AI は MCP 経由で使う**。プレイグラウンドを実際に触るのは
人間だけである。ここでの設計判断は、監査可能性や網羅性ではなく、人間の親指と
画面の広さに従う。

### 5.3 残したもの（画面積を取らない改修）

撤回は「バー・パレット配置・スワイプ除外」の 3 点に限る。以下は面積を取らずに
実害を消しているので残した。

- タップ判定（`touch-gestures.ts` の `createMultiTapRecognizer` /
  `checkIsStationary`）。ドラッグやピンチがプログラムを走らせない。
- `touch-action: manipulation`。ダブルタップ拡大とタップ数カウントの衝突を防ぐ。
- 入力欄 16px（iOS の自動ズーム防止）、隅のボタン 44px（絶対配置なので面積ゼロ）、
  パネルセレクタ 44px、検索欄の `min-width: 0`（13px はみ出しの修正）。
- 辞書の使用例の折り返し、補完の 2 文字発火。

逆に、ヘッダの `.btn` の 44px 床は戻した。ヘッダは 4 面すべての上にあるので、
そこの 10px は 4 面すべてから引かれる。元の 34px は親指が届く範囲だった。

### 5.4 代わりに厚くしたもの

記号パレットは**下端に貼り付く重畳**にした。開くのは必ず空のエディタなので
覆うのはプレースホルダだけであり、下端なら上から読み下せる。エディタは自分の
高さを 1px も失わない。

プレースホルダのチートシートを 7 行から 20 行に厚くした。**スマホではここが
タッチ操作の唯一の説明書**だからである。各行は 27 文字未満に収めてある——
テキストエリアのプレースホルダは幅で折り返すので、手で桁を揃えた継続行は
折り返しの残りに落ちて、360px では二段組が散文に崩れる。短い完結した行なら
どの幅でも同じ形で読める。360×740 で 20 行中 19 行が一目に収まる。

キーボードでしか届かない 4 操作（step / stop / look up / reset）は、その旨を
チートシートの最後に明記した。控えを供給できないなら、無いと言うのが正直である。
`spec/gui-semantics.md` の 4 本目の規範規則もこれに合わせて
**「Nothing a surface is reached by goes unsaid」**——「すべてに控えを用意せよ」
ではなく「控えが無いなら面がそう言え」——に書き換えた。控えは無料ではなく、
それが載る面から差し引かれる、という但し書きを規則本文に入れてある。

## 6. 辞書エリアも同じ勘定で（2026-09-21・所有者の報告）

§5 と同じ誤りが Dictionary 面にも残っていた。§3.3 で `.word-button` に敷いた
44px の床である。

### 6.1 測った結果

360×740 で Core Words 100 語の一覧は **1108px**、それを収める箱は **395px**。
**語彙の3分の2が画面の外**にあり、Ajisai に何があるかを知るにはスクロールして
覚えるしかなかった。320×690 では 1308px / 325px でさらに悪い。

床だけが原因ではなかった。`@container panel (max-width: 26rem)` が
「狭いパネルではチップを押しやすく育てる」として `font-size: 0.85rem` /
`padding: 0.4rem 0.6rem` / `margin: 3px` を当てており、モバイル列はこの条件に
当たる。コンテナクエリは**電話と細いデスクトップ列を区別できない**。

### 6.2 なぜ床に意味が無かったか

デスクトップではワードボタンはエディタに名前を打ち込む**操作子**なので、
押しやすさに面積を割く価値がある。モバイルでは違う——`onWordClick` は
`gui-application.ts` で `if (!mobile.isMobile())` に包まれており、**モバイルでは
何もしない**。タップして起きるのは要約と用例の表示だけである。つまりモバイルの
チップの仕事は「何が使えるかを見せる」ことと「ヒントを読める程度に押せる」ことの
2つで、44px の床が壊していたのは前者だった。

### 6.3 直し方——小さくしたのは字ではなく箱

| | 変更前 | 変更後 |
| --- | --- | --- |
| フォント | 13.6px（0.85rem・コンテナクエリ） | **12px（0.75rem・デスクトップと同じ）** |
| padding | 0.4rem 0.6rem | 0.1rem 0.25rem |
| margin | 3px | 1px |
| min-height | 2.75rem | なし |
| 100 語の行数（360px） | 22 行・1108px | **15 行・箱の中に収まる** |

字はデスクトップと同じ 0.75rem のままである。床が膨らませていたのは**字の周りの
箱**だった。コンテナクエリを無効化するには 3 プロパティすべてを後続の
メディアクエリで書き直す必要がある（`font-size` を書き忘れると 0.85rem が残る)。

辞書シートセレクタ（Core / User の切替）の 44px 床も外した。セッションに一度
触るだけの控えで、そこの 14px は一覧が欲しがっていた。パネルセレクタの床は
残した——あれは 4 面すべての到達手段である。

340px 以下だけ 0.65rem に落とす。箱が 411px でなく 341px しかなく、箱を締める
だけでは 6 語あふれるため。**字が小さくなるのはここだけ**である。

## 7. ヒント行を撤去し、ネイティブのツールチップへ（2026-09-21）

所有者の指示による。ヒント行（`.word-info-display`）を削除し、ワードの要約と
用例を `title` 属性——ブラウザ自身のツールチップ——に移した。

### 7.1 何だったか

ヒント行は `mouseenter` で書き込み `mouseleave` で消す、**手製のホバー表示**
だった。ホバーしていない間も面の1行を占有し、しかも表示するテキストによって
高さが変わるため、**ポインタがチップを横切るたびに下の一覧が再レイアウト**
していた。§6.4 の末尾で「デスクトップのクリックが動いたチップに着地することが
ある」と書いた現象の正体はこれで、今回の撤去で消えた（実測: ホバー20回で
チップの top 座標の変化なし）。

`title` はタイミングも配置も消去もブラウザが持つ。より原始的で、面を消費しない。

### 7.2 得たもの

| 画面 | 一覧の箱（撤去前 → 後） | 結果 |
| --- | --- | --- |
| 320×568 | 205 → 287px | 9 語が画面外（撤去前は 27 語） |
| 320×690 | 325 → 409px | 全語表示・86px 余裕 |
| 360×740 | 395 → 459px | 全語表示・127px 余裕 |
| 375×667 | 326 → 386px | 全語表示・76px 余裕 |
| 390×844 | 501 → 563px | 全語表示・253px 余裕 |

### 7.3 失ったもの——モバイルにヒントは出ない

**ツールチップはポインタを必要とし、電話にポインタは無い。** `title` はタップ
では出ないので、モバイルの辞書は「何があるか」を示すだけになり、「それが何を
するか」は示さなくなった。§6.2 で「モバイルのチップの仕事は2つ」と書いた
うちの片方が無くなったということである。これは指示による**受け入れ済みの
代償**であり、電話の読者が語の意味を知る経路はヘッダの Reference リンクになる。

元に戻したくなった場合、ヒント行を復活させるより安いのは、モバイルだけ
`click` で要約を出す小さな表示を足すことだが、それは面を消費する側に戻る
判断なので、必要になってから決める。

### 7.4 実装上の差

Core Words は要約と用例が名前と同じペイロードで届くので `title` は無償である。
User Word は `lookup_word_description` / `lookup_word_definition` の2呼び出しが
必要で、ホバー時ではなく**描画時**に読む——ツールチップはポインタが来る前に
文字列を持っていなければならないため。User 辞書の語数に比例した呼び出しが
毎描画で走るので、語数が3桁に乗ったときは遅延化を再検討する。
