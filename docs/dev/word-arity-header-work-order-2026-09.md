## 1. 問題

ユーザー語に掛けた `KEEP` は、呼び出しが実行時に**どれだけ深くスタックへ届いたか**で、
残すオペランドを決めている（`execute_builtin.rs` の depth watch）。その結果、次の 3 点が起きる。

1. `KEEP F` の意味は本体を走らせるまで決まらない。読み手も検査器も静的に知る方法がない。
2. ユーザー語をその本体で置き換えた Core のみのプログラムは、`KEEP` の直後で別の結果を出す。
   パイロットでは、この形の語がボトルネックで選ばれて継承され、21 解答に伝播した。
3. `EXEC` は `KEEP` を解除せずに本体を走らせるので、`KEEP` はブロックの最初の語に掛かる
   （`[ 3 ] [ 1 + ] KEEP EXEC` → `[ 3/1 ] 1/1 [ 4/1 ]`）。ユーザー語について
   「`KEEP` は呼び出しを修飾する」と直した理由が、ここではまだ効いていない。

## 2. 決定

### 2.1 パラメータ見出し

```
[ XS | XS SUM XS LENGTH / ] 'MEAN' DEF
```

- 定義本体の最上位（入れ子の外、最初の行）に最初に現れる `|` より前の名前が、その語の
  **パラメータ**である。個数がアリティになる。`[ | … ]` はアリティ 0 である。
- 見出しを持つ語は、**呼び出しで宣言した個数のオペランドをちょうど取る**。
  - スタックに足りなければ、Core 語と同じアリティ ERROR（スタック不足）になる。
  - 取ったオペランドは、深い方から順にパラメータへ束縛される（`[ A B | … ]` では、
    `A` が下の値、`B` が上の値）。
  - 本体は**空のスタックの上で**走る（MAP のブロックと同じ隔離フレーム）。
    束縛は障壁フレームなので、呼び出し元の束縛は見えない。
  - 本体が残した値すべてが、呼び出し元のスタックに積まれる（出力数は宣言しない）。
  - 本体が自分のフレームより下を読もうとすれば、スタック不足の ERROR になる。
- **`KEEP F` は、宣言した個数のオペランドを結果の下に残す。** 意味が字面で決まる。
- パラメータ名の条件は `BIND` の名前と同じ（字句として一語であること、Core 語・既存の
  ユーザー語と同名でないこと）に加えて、互いに異なることと、`|` でないこと。
  違反は `invalidDefinitionBody` の ERROR になる。
- **`|` は名前として使えなくなる**（`DEF` と `BIND` が拒否する）。字句文法は変えない。
  `|` は引き続き一つの Symbol トークンであり、区切りとして読むのは `DEF` だけである。
  空いていた文字を取るので、`character-allocation-and-prose-2026-09.md` の規準では
  「空き枠の消費」にあたる。

### 2.2 展開の忠実性（H5）

見出しを持つ語 `F`（パラメータ `A B`、本体 `body`）は、Core だけで次のように書ける。

| 呼び出し | Core のみの展開 |
| --- | --- |
| `F` | `'B' BIND 'A' BIND body` |
| `KEEP F` | `'B' BIND 'A' BIND A B body` |

どちらも `EXEC` を経由しないので、§1.3 の問題に触れない。本体が自分のフレームの外を
読まない限り（読めば `F` は ERROR になる）、この展開は同じ観測を与える。束縛名が
呼び出し元の名前と衝突しないよう、展開する側で改名する。

### 2.3 `EXEC` と `KEEP`

`KEEP EXEC` は、`EXEC` の呼び出しを修飾する。ブロックの中へは漏らさない。
本体は消費モードで走る。Phase 1 では、`EXEC` が届いた範囲を見出しのない語と同じ規則で
結果の下に戻していた（`restore_kept_operands`）。Phase 3 でこれを静的な規則に改めた（§5.1）。

### 2.4 内容同一性

見出しを持つ語の内容同一性では、パラメータを名前ではなく**位置**で符号化する。
パラメータ名だけが違う二つの定義は、同じ語になる（DIGEST が一致する）。
パイロットで計測器側に D0α を足さなければならなかった問題は、見出しを使う語については
言語の側で消える。本体内の `BIND` の名前は、この段では正規化しない。

### 2.5 契約推論

見出しを持つ語の推論では、次のとおりにする。

- `inputs` は宣言したアリティ n そのものとする。
- パラメータ名の出現は値を一つ積む操作として扱い、`gap.unresolvedWord` にしない。
- 本体の中の `'NAME' BIND` が作る名前も同じく値一つとして扱う（見出しのない語にも効く。
  パイロットの計測器所見 M-2 の解消）。
- 本体がフレームより下を読む定義は、呼び出しのたびにスタック不足の ERROR になる。
  スタック効果が固定の本体については、Phase 3 で `DEF` が定義時に拒否するようにした（§5.1）。

### 2.6 見出しを持たない語（移行期間）

見出しを持たない本体は、**現行どおり**（スタック全体を見るフレーム、`KEEP` は動的）とする。
既存の定義はおよそ 750 箇所あり、その各々のアリティを機械的に決める手段がないので、
一度には移行しない。

| Phase | 内容 |
| --- | --- |
| 1（PR #1718、実施済み） | 見出しの導入、`EXEC` の修正、同一性・推論・表示・永続化の対応、仕様・適合テスト・SKILL.md |
| 2（実施済み、§4） | リポジトリ内の定義を見出し付きへ移行する（テストが決める） |
| 3（実施済み、§5） | 見出しを必須にし、スタック全体を見るフレームと動的 `KEEP` を削除する。ユーザー語の本体の規則が一つになる |

## 4. Phase 2 の実施記録

### 4.1 方法

`scripts/migrate-def-headers.mjs` が、ファイル中の `[ body ] 'NAME' DEF` を機械的に書き換える。

- **アリティの決め方**: 本体を走らせずに、`spec/words.json` の Core のスタック効果と、同じ
  ファイルで先に定義された語のアリティを使って、本体を模擬する。本体の下から読む個数が
  アリティである。`EXEC`、未知の名前、数の決まらない `COLLECT` を含む本体は書き換えない。
- **書き換えの形**（どちらも、ちょうど n 個を読む本体について意味を保つ）:
  - 本体が `'V' BIND` で始まるものは、束縛名をそのまま見出しに移す: `[ 'V' BIND V … ]` → `[ V | V … ]`
  - それ以外は、名前を付けてオペランドを積み直す: `[ 2 * ]` → `[ X | X 2 * ]`
  - 入力のない本体には空の見出しを付ける: `[ [ 1 ] [ 2 ] + ]` → `[ | [ 1 ] [ 2 ] + ]`

### 4.2 結果

| 対象 | 書き換え | 残置 |
| --- | --- | --- |
| 読み物と仕様のソース（`spec/*.json`・適合テスト・ja Reference・MCP の評価事例と selftest・SKILL の生成元ほか） | 79 | 19 |
| Rust と TypeScript のテスト・例 | 233 | 51 |

書き換え後に失敗したテストは 3 件で、いずれも字面に結び付いた期待値（トークン数、
保持した本体の表示、GUI のステップ分割）だった。振る舞いの違いによる失敗はなかった。

残置した箇所は、次のどれかに当たる。

- テストの書式文字列（`{body}` など）
- 再帰・循環の拒否を確かめるテスト
- 未知の語や退役した語の診断を確かめるテスト
- `EXEC` を含む本体
- 後で定義される語への前方参照の連鎖

見出しのない語の振る舞い（`KEEP` が呼び出しの届いた範囲を残す）は、Phase 3 まで
存在するので、`param_header_tests.rs` の一件で明示的に固定した。

ja Reference の散文のうち、見出しで意味が変わる箇所は手で直した（ブロックの評価文脈の表、
`ADDW` の説明、`ID` の定義）。`DEF` の節には見出しの説明を加えた。

## 5. Phase 3 の実施記録

### 5.1 決定

| 項目 | 内容 |
| --- | --- |
| 見出しの必須化 | `DEF` は見出しのない本体を `invalidDefinitionBody` で拒否する。ユーザー語の本体の規則は「宣言したフレーム」だけになり、スタック全体を見る規則は `EXEC` にだけ残る |
| 動的 `KEEP` の削除 | 呼び出しが届いた深さを測る仕組み（`Stack` の depth watch と `restore_kept_operands`）を削除した。`KEEP` が残すものは、どの呼び出しでも字面で決まる |
| `KEEP EXEC` | ブロックのフレームはスタック全体なので、呼び出しに渡されたのはスタック全体である。`KEEP EXEC` はスタック全体を残し、その上にブロックが残したものを積む。`1 [ 3 ] [ 1 + ] KEEP EXEC` は `1 [ 3 ] [ 1 + ] 1 [ 4 ]`。Phase 1 の動的な読み方（`1 [ 3 ] [ 1 + ] [ 4 ]`）より冗長だが、実行しなくても決まる。拒否（ERROR）にする案もあったが、新しい失敗の種類を増やさずに済むこちらを選んだ |
| フレーム外読みの定義時拒否 | `DEF` は本体を Core 展開（`'B' BIND 'A' BIND body`）の形で契約推論にかけ、スタック効果が固定で、見出しの個数より多く消費するなら `invalidDefinitionBody` で拒否する。効果が値に依存する本体（`EXEC` や、効果の決まらない語を含むもの）は拒否せず、実行時にスタック不足になる |
| 保存済み辞書 | 見出しのない定義は、読み込み時に `DEF` が拒否する。既存の仕組み（`restore_user_word_definitions` の skip）で、その語だけを飛ばして理由付きで報告し、他の語は復元する。アリティは字面から読めないので、自動で見出しを補うことはしない |

### 5.2 移行

Phase 2 で残した箇所は、すべて手で見出し付きにした。対象は次のとおり。

- テストの書式文字列
- 再帰・循環の拒否を確かめる例（`spec/termination.json`・`spec/outcome-witnesses.json`）
- 未知の語の診断
- `EXEC` を含む本体
- 前方参照の連鎖

GUI が最初に入れる例語（`src/gui/example-words.ts`）と、語彙創発実験のプロンプトも見出し付きにした。
`docs/dev/` の過去の作業指示書と、記録された評価トランスクリプトは履歴なので書き換えていない。
