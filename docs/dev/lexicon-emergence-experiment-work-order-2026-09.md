## 0. この文書の読み方（実装者向け・最初に必ず読む）

### 0.1 問い

Ajisai の Core 100 語は人間（と人間に指示された AI）が選んだ。本実験は逆向きに問う。

> **Core を固定したまま AI どうしに実務課題を共同で解かせ、共有辞書に伝達の
> ボトルネックをかけたとき、独立に何度も再発明され、同じ定義へ収束する語は何か。
> 逆に、誰も使わない Core 語はどれか。**

収束した語は、語彙に欠けているものの経験的証拠になる。使われない Core 語は、
§7.4 の退役候補の列を検証する材料になる。言語学の対応でいえば、Core が
普遍文法（生得・封印）、User 辞書が習得される語彙目録にあたり、本実験は後者の
創発を観察する。

### 0.2 背景となる知見（本実験の設計が依拠するもの）

- 創発コミュニケーション研究では、構成性（部品の組み合わせで意味が決まる性質）は
  自然には生じず、**伝達のボトルネック**（語彙容量の制限と、世代交代による学び直し）
  の下で生じることが繰り返し報告されている（Kirby らの反復学習）。本実験の
  操作変数はこのボトルネックである。
- 2017 年に報じられた交渉エージェントの「独自言語」は、人間向けの規則を保つ圧力が
  消えたことによる符号の漂流だった。本実験は漂流を許すが、**すべての発話が Core
  まで展開でき、停止し、再生できる**という Ajisai の性質で監査可能性を担保する。
  これが観察対象の一つでもある（§3 H5）。

### 0.3 記述規律

- 本書の「計測器の実測」（§2）は、**2026-09-23 にこのリポジトリの MCP サーバー
  （`ajisai-mcp-server 0.3.0`、engine `0.2.0-alpha.1`、`wasmWorker` backend）で
  実行した結果だけ**を書いている。実行していない推測は「未確認」と書く。
- 実験結果の報告では、測っていない効果を書かない（`devlog-format.md` の誠実性の
  規律に従う）。

### 0.4 禁止事項

- 実験結果を根拠に `spec/` を直接書き換えない。結果は §7.3 の規則に照らして
  **所有者判断へ提出する候補**であり、採否は別 PR で行う。
- 収束の指標に DIGEST の不一致を「別の語」の証拠として使わない。DIGEST は一方向に
  しか決定しない（`LANG.DICTIONARY.MUTATION`、`spec/identity.json`）。不一致は
  「同じと示せなかった」でしかない（§2.2 の D1 で補う）。
- 課題の正解判定を LLM に委ねない。判定は常に `compute` の実行結果と期待値の照合で行う。
- 実験用に Core を変更しない。変更した Core で走らせた結果は、本書の結果として
  報告しない。

### 0.5 停止条件（詰まったら黙って続行せず報告する）

- Phase 1 で、同一モデルの複数エージェントがほぼ同一の定義を初手から出す
  （= 創発ではなく事前分布の反映に見える）場合。§5.3 の統制を先に強化するか、
  所有者に差し戻す。
- 課題セットの正答率が Phase 1 で 30% を下回る場合。語彙の問題ではなく課題か
  SKILL.md の問題なので、実験を止めて原因を切り分ける。
- MCP サーバーの応答が `hostError` を返す課題が 5% を超える場合（実装欠陥の
  混入。`mcp-hard-use-findings-work-order-2026-09.md` の F-1 系を先に疑う）。

## 2. 計測器 — DIGEST が何を同一視し、何を同一視しないか（実測）

収束の主指標は `DIGEST`（内容同一性）である。使う前に、その粒度を実測で固定した。

### 2.1 実測結果

| # | 入力 | 結果 | 含意 |
| --- | --- | --- | --- |
| 1 | `[ [ 2 ] * ] 'DBL' DEF [ DBL ] 0 GET DIGEST` と `... 'TWICE' DEF [ TWICE ] ...` | 同じ `#843e9e8f…` | **名前は同一性に入らない** |
| 2 | `[ DBL DBL ] 'QUAD'` と `[ X2 X2 ] 'Q4'`（依存語も別名） | 同じ `#b00fefe0…` | **推移的にも名前非依存**。独立に命名した語が同じハッシュに落ちる |
| 3 | `[ [ 2 ] MUL ]` と `[ [ 2 ] * ]` | 同じ `#843e9e8f…` | 別名（alias）は正規化される |
| 4 | `[ 2 * ]` と `[ [ 2 ] * ]` | 別（`#97c9…` / `#843e…`） | 字面が違えば別。ただし下の #5 のとおり、これは正しい区別である |
| 5 | `3 [ 2 ] *` → `[ 6/1 ]`、`3 2 *` → `6/1`。Vector 入力 `[ 1 2 ]` ではどちらも `[ 2/1 4/1 ]` | — | #4 の二語は**スカラー入力でだけ振る舞いが違う**。観察的同値の判定に Vector だけの探針を使うと誤って同一視する |
| 6 | `[ [ 2 ] SWAPLESS ] 'D' DEF`（未定義の名前を本体に含む） | `ok` | DEF は本体の名前を定義時に解決しない。共有辞書に入れる前に `check` が必要 |
| 7 | `A` に依存する `B` があるとき `A` を再定義 / 削除 | `ERROR`（`referenced by B`） | 被依存語の名前は事実上不変。エージェント間で名前が衝突すると後着が定義できない |
| 8 | `[ [ 2 ] * ] 'DBL' DEF [ DBL ] 0 GET CONTRACT` | `{ 'inputs' 1/1 'outputs' 1/1 … 'confidence' 'complete' … }` | 推論契約がそのまま語の「型」の要約として使える |

### 2.2 同一性の三段階

実測 #4〜#5 から、収束は三段階で数える。

| 段 | 名称 | 判定 | 性質 |
| --- | --- | --- | --- |
| D0 | 構文同一 | `DIGEST` が一致 | 健全（一致すれば同じ語）。不一致は何も言わない |
| D1 | 観察同値 | 探針セットの全入力で `compute` の結果（stackDisplay と NIL 理由）が一致 | 探針に依存する。**探針はスカラー・1 要素 Vector・多要素 Vector・入れ子・NIL レーン・Record を必ず含める**（#5） |
| D2 | 契約同形 | `CONTRACT` の inputs / outputs / purity / nil が一致 | 粗い。D1 の候補の絞り込みにだけ使う |

D1 の探針セットは語の推論契約（D2）の入力数から生成し、seed 固定で再現可能に
する（`RANDOM` は seed を取る純粋な語なので Ajisai 内でも生成できる）。

### 2.3 実測 #6・#7 への対処（実験の運用規則）

- 共有辞書へ登録する前に、定義本体を `check` に通し、未解決の名前が残る定義は
  登録しない。
- 名前衝突を避けるため、エージェントは自分の接頭辞付きの名前（`A3.DBL` など、
  字句文法が許す文字で）で DEF する。**共有辞書のキーは名前ではなくハッシュ**とし、
  名前は各エージェントの「方言」として記録する。これは A1 案（ハッシュ不変辞書）を
  実験の外側で先取りしたものに当たる。

## 3. 仮説と指標

| ID | 仮説 | 主指標 | 反証条件 |
| --- | --- | --- | --- |
| H1 | 独立したエージェントは、同じ下位問題に対して同じ語を再発明する | D0/D1 で同値類を作ったとき、2 系統以上から独立に到達された同値類の数と割合 | 独立到達の同値類がほぼない |
| H2 | ボトルネック条件では、無制限条件より辞書が構成的になる | 辞書内の語のうち、他の辞書語を本体に含む語の割合／語の依存深さの分布 | 両条件で差がない |
| H3 | 収束した語の一部は、§7.3 条件 1（言語内で書けない、または漸近的に高くつく）を満たす候補を指す | 収束語のうち、`CONTRACT` の cost が同じ仕事の自然な Core 実装より悪いクラスになるもの | 該当なし（それ自体が「今の Core に穴はない」という結果になる） |
| H4 | §7.4 の退役候補の列の上位語は、実際にも使われない | Core 語ごとの使用頻度（解答中の出現、辞書語経由の推移的出現を含む） | 列の上位語が高頻度で使われる |
| H5 | 辞書が圧縮され方言化しても、発話は Core まで機械的に展開でき、人間が監査できる | 全解答について、辞書語を再帰的に展開した Core のみのプログラムが元と D1 同値になる割合（目標 100%） | 100% を下回る（= 監査可能性の欠陥。最優先で報告する） |

補助指標:

- **圧縮率**: 辞書ありの解答トークン数 ÷ 辞書なしの解答トークン数。
- **正答率**: 各世代の課題正答率（辞書が「役に立つ語彙」になっているかの確認）。
- **修復回数**: 正答に至るまでの `compute` の呼び出し回数。

## 4. 課題セット

- 基盤は `tools/mcp-server/eval/cases.json`（79 件、en/ja の自然文プロンプトと
  期待値付き）。ただしこれは単発の小問が中心なので、語が再利用される余地が少ない。
- そこで**下位問題を共有する課題族**を新たに作る。1 族 5〜8 問、族内の問題は
  同じ下位計算（例: 移動平均、正規化、キーでの集約、区間の重なり判定、
  文字列の分割と整形、収束計算の有限打ち切り）を異なる文脈で要求する。
- 族は 6〜10 個（数値・コレクション・Record/データ・テキスト・混合）。
- 各問は `{ prompt, expect }` 形で、`expect` は `cases.json` と同じ JSON Pointer
  照合を使う。期待値は人間が作り、**課題作成者と被験エージェントは別の文脈**とする。
- 課題ファイルは `tools/lexicon-emergence/tasks/` に置く。

## 5. 手順

### 5.1 一世代の流れ

1. 世代 g のエージェント群（N 体、互いに独立した文脈）それぞれに、次を与える。
   - SKILL.md（全員同一の版を固定）
   - 共有辞書 L_g のうち容量 K 件（各項目: ハッシュ、代表名、推論契約、使用例 1 つ）
   - 課題族からランダムに割り当てた問題
2. エージェントは MCP で試行し、解答プログラムを提出する。必要なら新語を DEF して
   よい。提出物は「使った辞書語」「新たに定義した語」「解答本体」に分けて記録する。
3. 採点は `compute` で行う（§0.4）。
4. 正答した解答に含まれる語（新語と既存辞書語）について、使用回数を加算する。
5. 新語を §2.2 の D0/D1 で既存の同値類に統合する。
6. 次世代の辞書 L_{g+1} を作る。**使用回数の上位 K 件だけを残す**（ボトルネック）。
7. 次世代は新しい文脈のエージェントとし、前世代の会話を一切引き継がない。
   引き継がれるのは L_{g+1} だけである（反復学習）。

### 5.2 条件

| 条件 | K（辞書容量） | 世代交代 | 目的 |
| --- | --- | --- | --- |
| C-bottleneck | 小（例 16） | あり | 本条件 |
| C-open | 無制限 | あり | H2 の対照 |
| C-solo | — | なし（辞書を共有しない） | H1 の基準線。独立到達の偶然率を測る |
| C-shuffled | 小 | あり | 辞書の代表名を意味のない名前に置換。名前の意味に頼った再利用かを切り分ける |

### 5.3 統制（同一モデルの事前分布を創発と誤認しないために）

同じモデルの複数体が同じ定義を出すのは、創発ではなく共通の事前分布の反映でありうる。
これが本実験で最大の交絡である。

- C-solo の独立到達率を基準線とし、H1 はその**超過分**で評価する。
- 経路 B では、世代内にモデルの異なるエージェント（大・中・小の 3 系統）を混ぜる。
  系統をまたいで収束した同値類を、系統内の収束より強い証拠として扱う。
- 温度など生成パラメータを記録し、条件間で揃える。

### 5.4 H5（監査可能性）の検査

全解答について、辞書語を定義本体で再帰的に置き換えて Core 語だけのプログラムを作り、
元の解答と D1 同値であることを `compute` で確かめる。展開には名前ではなく
ハッシュの対応を使う（§2.3）。一件でも失敗したら、その解答と辞書の状態を保存して
報告する。これは Ajisai の売りそのものの反例になりうるので、他の結果より優先する。

| Phase | 内容 | 規模 | 完了条件 |

**着手前に所有者の承認を得る**。

### 6.1 Phase 2 の実装（経路 B）

`tools/lexicon-emergence/lib/harness.mjs` と `cli.mjs run` / `cli.mjs pilot` が経路 B である。

- **道具**: 被験者に渡す道具は、MCP サーバーが公開している `compute` / `check` / `word_contract` の定義そのままに、提出用の `submit` を加えたもの。ハーネスは呼び出しをサーバーへ中継し、返ってきたテキストを変えずに返す。経路 A との違いは次の 2 点だけである。
  - SKILL.md を読む手段: 経路 A では被験者が自分でファイルを読んだ。経路 B ではシステムプロンプトに入れる（全被験者で同じバイト列にして、キャッシュを効かせる）。
  - 提出の手段: ファイルへの書き込みではなく `submit` ツールで提出する。
- **統制**:
  - モデルは `--model` で固定する（`large` / `medium` / `small` = Opus 5 / Sonnet 5 / Haiku 4.5）。
  - 応答ごとに、実際に応答したモデル（`response.model`）を記録する。
  - サーバー側の refusal fallback は使わない。使うと応答モデルが入れ替わり、§5.3 が統制する変数を崩すからである。refusal はその被験者の終了理由として記録する。
  - 生成パラメータ: 温度は現行モデルでは指定できない。代わりに effort を記録し、条件間で揃える。
- **費用**:
  - 上限を USD で指定する（`--budget`）。リクエストのたびに、公表単価と実際の usage から計算した累計を照合する。
  - 被験者ごとの費用、ターン数、全メッセージを `transcripts/` に残す。
- **検証**: 擬似モデル（API を呼ばない）で、実サーバーと実採点器を通す試験を置いた（`npm test`）。
- **未実施**: API での Phase 1 再現（`node cli.mjs pilot <run> --budget <USD>`）。実行には環境変数 `ANTHROPIC_API_KEY` が要る。
  - 見積もり: SKILL.md が約 12k トークンで、被験者 1 体あたり 20〜40 リクエスト。Opus 5 で 1 体あたり約 $1〜4、パイロット規模（12 体）で約 $15〜50。
  - 実測値が出たら、Phase 3 の見積もりの根拠として本節に追記する。

## 8. 既知の限界

- 被験者が Ajisai の文書（SKILL.md）から学ぶ以上、語彙は文書の例に引きずられる。
  版を固定して記録し、結果の一般化はその版に限る。
- 課題族を作るのは人間なので、「どの下位問題が繰り返し現れるか」は課題設計が決める。
  収束語は「その課題分布の下で有用な語」であり、言語一般の欠落を直ちには意味しない。
- D1 は探針セットに依存する。D1 で同値とされた類は、D0 で一致するまで
  「探針上で区別できなかった」とだけ報告する。
- 全域言語なので、収束計算など一部の下位問題は有限の打ち切りとして表現される。
  打ち切り方の違いで同値類が割れることを想定して、割れた類は注記する。
